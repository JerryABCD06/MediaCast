## 1. 最终目标

固定为三个进程：

| 代号 | 进程 | 职责 |
|---|---|---|
| A | `MCast.Protocol.exe` | 原生 Win32，无 Qt；SSDP、HTTP、SOAP、GENA、网络会话 |
| B | `MCast.Ui.exe` | Qt/QML、FluentUI、MainWindow、libmpv |
| C | `MCast.Shell.exe` | 原生托盘、启动屏幕、配置、SMTC、进程监督 |

硬约束：

1. 未打开 MainWindow 时，`MCast.Ui.exe` 不存在，Qt/QML/OpenGL/libmpv 都不驻留。
2. A 不能直接启动 B；A 只能向 C 发 `UiActivateRequest`，由 C 启动 B。
3. C 是唯一有权启动、停止、重启 A/B 的进程。
4. A 是网络会话和逻辑播放状态的权威；B 是实际播放测量和渲染的权威；
   C 是持久配置和进程状态的权威。
5. DLNA 对象、XML、SOAP 名称不得泄漏到 MainWindow 或播放器层。
6. 所有新代码使用 `MainWindow`，不再新增 `NewUi` 命名。
7. C 崩溃时 B 退出；A 负责重启 C。B 崩溃时 C 清理并允许下一次激活。

## 3. 进程入口契约

```text
双击 MCast.Shell.exe
  -> 解析最少参数
  -> 第一步创建当前用户的单实例 Mutex
  -> 已有 Shell：
       通过 ShellCommands 命名管道发送 argc/argv 与工作目录
       已有 Shell 返回 Ack，新进程回 Complete 并等待 FinalAck 后退出
  -> 没有 Shell：
       成为唯一主实例
       ShellRuntime 构造启动屏幕绘图线程
       初始化 Job、首帧事件、ControlPipe
       启动 Protocol；背景模式不发送 --request-ui
       Protocol 完成 Control Hello 后，只有主动发 UiOpenReady 的空闲
       Protocol 才可接收打开命令
       开放 ShellCommands 监听和命令线程
       普通二次启动 -> C 向 A 发 UiOpenRequest
       A 沿正常 UiActivateRequest 流程请求 C 打开 MainWindow

直接启动 MCast.Protocol.exe / MCast.Ui.exe
  -> 没有合法 Shell 上下文：失败关闭
  -> 不创建网络服务、窗口、Qt/QML 或托盘
  -> 开发独立运行必须显式传 --standalone
```

约束：

- Shell 单实例锁必须早于 Splash、托盘、IPC 和子进程初始化。
- ShellCommands 可以早于 Protocol Hello 接受连接，但普通打开命令必须等待
  Protocol 完成身份握手并声明 `UiOpenReady`；不能仅以子进程创建成功代替
  “Protocol 当前处于可接命令状态”。
- 第二次启动不能只报“已经运行”；必须完成 Request → Ack → Complete →
  FinalAck 交接后再退出。
- ShellCommands 管道使用当前用户 SID ACL，连接启用
  `SECURITY_IDENTIFICATION`，并双向校验对端与当前 Shell 可执行文件哈希一致。
- `--background` 交接只强化后台存在，不打开 MainWindow。
- 普通双击交接表达“打开 MainWindow”；没有 Ui 时由 Protocol 发起激活，
  已有 Ui 时复用当前代次并尝试把主窗口带到前台。
- 后台 Protocol 必须跨 Ui 生命周期常驻；Ui 退出后重新发送
  `UiOpenReady`，同一 Shell 仍可再次打开 MainWindow。
- 生产模式的前台与后台 Protocol 都常驻；有限 Ui 轮次只属于测试模式。
- 生产模式只接受默认实例名；`--instance` 自定义值仅供 `--test` 隔离测试。
- 交接失败且旧 owner 已消失时，二次进程有限重试 Mutex 接任；
  “获取 Mutex”与 Shell 完整初始化作为一个可重试整体，等待旧命名管道句柄释放。
- Protocol/Ui 由 Shell 启动时必须携带 instance、nonce、Shell PID；Ui 还必须有 activation ID。

## 4. 打开 MainWindow 的准确流程

```text
手机请求到达 A
  -> A 校验协议、URI、会话和 deadline
  -> A 在 ControlPipe 发送 UiActivateRequest(message_id, session_id)
  -> C 校验 A 的身份与方向
  -> C 检查当前 Ui：
       · 还活着：返回 started=false，不启动第二个 B
       · 已退出但尚未被主循环 reap：同步清理旧记录
       · 没有 Ui：分配新的单调 activation ID，返回 started=true
  -> C 先等待启动屏幕绘图线程真实 Shown，再 suspended 启动 B
  -> C 将 B 放入 Job Object，然后 resume
  -> C 向 A 返回 UiActivateDecision(started, activation_id)
  -> started=true 时，C 再向 A 返回 B 的 PeerIdentityGrant
  -> B 连接 ControlPipe，发送 Hello
  -> C 验证 PID、nonce、build ID、EXE hash
  -> C 返回 HelloAck，并向 B 下发 A 的 PeerIdentityGrant
  -> B 连接 PlaybackPipe，再次 Hello/HelloAck
  -> B 请求 SessionSnapshot
  -> A 返回带 state_version 的 Snapshot
  -> B 创建 MainWindow，grabWindow 离屏预热，然后 show
  -> QQuickWindow 完成首次 frameSwapped
  -> B 上报 UiFirstFrame(correlation_id=activation_id)
  -> C 只接受当前 activation ID
  -> C 淡出启动屏幕
```

必须保持：

- SOAP 响应不得同步等待 QML 创建、首帧或 `grabWindow()`。
- `UiActivateRequest` 在 Ui Starting/Running 时按当前代次合并。
- Ui 已退出但 Shell 尚未轮询清理时，新请求也必须同步发现并启动新代次。
- 复用已运行 Ui 时返回 `started=false`，A 不再等待一个新的 PlaybackPipe。
- C 只在 `started=true` 时下发新的 Ui identity grant。
- stale `UiFirstFrame` 不得被当前代次接受。

## 5. Ui 退出与故障时序

### 用户关闭 MainWindow

```text
B 发出 windowClosed
  -> QApplication::quit
  -> B 进程退出，Qt/libmpv 全部卸载
  -> C 发现 Ui 进程结束
  -> C 终止并淘汰旧 ChildRecord，UiState=None
  -> 下一次 UiActivateRequest 分配新的 activation ID
```

不得删除 Ui 记录的依据是“网络暂时不好”；只有进程退出或明确关闭才清理。

### Ui 启动失败或首帧超时

- C 立即收起启动屏幕，终止失败的 Ui，淘汰记录并允许后续激活。
- C 不再因为 Ui 超时退出整个 Shell；A/C 继续监督服务。
- 当前尚未把 Ui 启动失败编码成 A 能转发给控制点的明确协议错误；这是后续
  `UiActivateDecision` 失败分支要补的部分。
- 不允许同时启动第二个 Ui。

### Shell / Protocol 崩溃：目标语义

- 目标：Shell 崩溃后 B 退出；A 不随 Shell 一起被无条件杀死，并负责重启 C。
- 目标：Protocol 崩溃由 C/B 发现，C 在预算内重启 A。
- **当前限制**：A/B 尚在同一个 `KILL_ON_JOB_CLOSE` Job 中，Shell 崩溃会一起
  杀死 A/B；Shell 目前也只监督 Ui，没有 Protocol 重启状态机。
- 在 A 改为跨 Shell 生命周期存活之前，不得把上面两条写成“已实现”。

## 6. 子进程记录规则

- `findRecord()` 返回的裸指针只能在 `m_recordsMutex` 持有期间解引用。
- 跨锁使用必须复制 PID、build ID、nonce、EXE hash、expectation 等值。
- 锁顺序固定为 `m_uiMutex -> m_recordsMutex`，不得反向。
- `m_activationId` 表示当前代次；`m_nextActivationId` 只增不减。
- 首帧计数是原子量；UiState 和当前代次受 `m_uiMutex` 保护。

## 8. 开发协作约束

- 界面点击、拖动、悬停由用户本人操作；助手负责启动、日志、转储和静态分析。
- 未经请求不要删除未跟踪文件；当前无关文件 `16` 必须保留。
- CRLF/LF 可能造成大量假修改；只精确暂存实际变更文件。
- 每次较大改动都要构建、跑测试，并交子代理做只读静态复审。
- PowerShell 递归删除可能被策略拦截；不要用宽泛路径删除。
- 启动屏幕的 HWND、D3D/D2D 资源和窗口类必须在绘图线程退出前显式销毁。
  否则本机注入的 `wetype_tip.dll` 可能在进程退出时于卸载路径触发
  `0xC0000005`；`SplashUi::~SplashUi()` 已专门处理这一步。
- `MCast.Shell.exe` 运行时和链接目标都不依赖 Qt；当前整个 CMake 工程仍统一
  `find_package(Qt6)`，且构建 Shell 会连带构建 `MCast.Ui`。重构完成前不要把
  “Shell 无 Qt”误解成“整个构建图不安装 Qt 也能配置”。

## 9. 下一步顺序

   显示/隐藏状态由绘图线程真实回调，整个 Shell 链接目标不依赖 Qt。下一步接
   持久主题/强调色配置。
2. **托盘已迁进 Shell**：原生 Win32 通知区已实现“打开 MainWindow /
   暂停接收 / 退出”；暂停状态经独立 `ProtocolCommands` 管道发给 A。
3. **把正式网络实现迁进 `MCast.Protocol.exe`**：先搬 SSDP/HTTP/SOAP/GENA，
   保持 wire-level 行为不变，再补会话状态机。
4. **持久化 PlaybackPipe**：B 保存连接，应用 Snapshot 和后续增量状态。
5. **替换旧 `MCast.exe` 入口**：新入口稳定后再删除旧单体路径。
6. **最后替换 libmpv 0.42.0 DLL**：替换后做实际视频/音频/字幕/全屏回归。
