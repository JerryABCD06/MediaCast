## 1. 目标与真实层边界

任何时刻最多一个投送 owner。DLNA、未来的 Google Cast、AirPlay、Miracast 和
厂商协议都通过一个中性 `ClaimRequest` 竞争所有权。

- `CastArbiter` / `CastClaimCoordinator` 在 Protocol 进程内，不认识 Qt。
- Shell 不解析 SOAP/Cast/AirPlay。
- UI 不判断协议动作是否合法，只显示 Shell 转来的中性确认请求。
- 确认前旧 owner 继续播放，owner 和 epoch 不变。
- 拒绝、关闭、超时、UI 不可用都 fail-closed。

当前真实接入协议的只有 DLNA。其他协议类型已经出现在中性枚举中，但尚无适配器。

## 2. 策略对象与生产值

`ArbitrationPolicy` 包含：

```text
allowPreemption
confirmPreemption
confirmationTimeout
retirementTimeout
maxRetiringSessions
```

通用结构体的保守默认值是“禁止抢占、需要确认”，但真实生产 DLNA Runtime 当前
显式使用：

```text
allowPreemption      true
confirmPreemption    true
confirmationTimeout  10 s
retirementTimeout    5 s
maxRetiringSessions  8
```

因此不要把通用默认值当作当前手机行为。也请注意：

- `cast.newcast` 是“是否接收新投送”；
- 它不是“是否允许抢占”；
- UI 设置页尚未持久化抢占策略。

## 3. 唯一状态

`ArbitrationSnapshot` 至少包含：

```text
revision
phase = Idle / Preparing / Active /
        ActiveWithPendingClaim / IdleWithPendingClaim /
        Handoff / Faulted
owner
pendingClaim
retiringSessions
lastEpoch
lastFailure
```

不变量：

1. owner 最多一个。
2. pendingClaim 最多一个。
3. 只有所有权真正改变才递增 epoch。
4. pending 出现、消失或退场变化可以递增 revision，但不改变 owner。
5. retiring session 不是 owner，不能继续驱动播放器或 UI。
6. 旧 session 的命令、完成和事件必须按身份/代次丢弃。

Claim 幂等键是 `(protocol, claimId)`。当前 owner、pending 和 Shell 最近确认结果
共同承担重复识别；协议适配器不应依赖无限期回放旧 Claim ID。

## 4. 状态转换

### 空闲首次投送

```text
Idle
  -> Claim Accepted
  -> Preparing
  -> sessionReady
  -> Active
```

首次投送不弹确认。

### 禁止抢占

```text
Active(old)
  -> new Claim
  -> Busy
```

旧 owner、pending 和 epoch 都不变。

### 立即抢占

```text
Active(old)
  -> Accepted(Preempted)
  -> Handoff(new, retiring=[old])
  -> sessionReady(new)
  -> Active(new, retiring=[old])
```

新会话可以开始准备，旧会话并行走场；旧会话不能再修改中央状态。

### 抢占前确认

```text
Active(old)
  -> AwaitingConfirmation
  -> ActiveWithPendingClaim(old, candidate)
```

用户确认：

```text
ActiveWithPendingClaim
  -> DLNA Stop(old)
  -> Handoff(candidate, retiring=[old])
  -> Open(candidate)
```

用户拒绝或 10 秒超时：

```text
ActiveWithPendingClaim
  -> Active(old)
```

候选控制点在 SetAVTransportURI 之前发送的 Stop 只完成 DLNA HTTP 响应，
不进入 Playback、不修改 owner/media，也不发布控制点身份。确认接受后，DLNA
先 Stop 旧 owner，只有 Stop 成功才提交 Handoff 并 Open 新媒体；确认拒绝、
超时或 Stop 失败都不改变旧 owner。

确认函数自己也会检查绝对 deadline；即使调度器尚未 `tick()`，到点后的确认也不能
成功。

### 旧 owner 在待确认期间自然结束

```text
ActiveWithPendingClaim(old, candidate)
  -> IdleWithPendingClaim(candidate)
```

候选仍保留原 deadline。接受后从 Idle 建立新会话，不再算“抢占”。

## 5. 确认消息链

```text
Protocol -> Shell   CastConfirmationRequest
Shell -> UI         UiCastConfirmationRequest
UI -> Shell         UiCastConfirmationDecision
Shell -> Protocol   CastConfirmationDecision
```

取消与断线：

```text
Protocol -> Shell   CastConfirmationCancel
Shell -> UI         UiCastConfirmationCancel
```

请求携带中性字段：

```text
protocol
claimId
peerId
peerDisplayName
peerAddress
mediaTitle
remainingTimeoutMs
```

确认消息的 `sessionId` 和 `stateVersion` 固定为 0；候选还没有 session 所有权。
关联使用 `messageId + correlationId + protocol + claimId`。

IPC 当前版本是 1.4。Protocol↔Shell 确认消息要求最低 minor 1，Shell↔UI 确认消息
要求最低 minor 2。

## 6. Shell 与 UI 的 generation

Shell 分开维护：

- `protocolGeneration`：Protocol Control 连接注册/清除时递增；
- `uiGeneration`：UI Control 连接注册/清除时递增。

每个 pending 保存创建时的 UI 连接、UI generation 和绝对 deadline：

- decision 必须来自同一连接和同一 generation；
- UI 重连只取消旧 generation 的 pending；
- cancel 必须发给创建该 pending 的原 UI 连接；
- 最近结果缓存由 **Shell** 持有，最多 32 项，并绑定 protocol generation；
- Protocol/UI 换代时清空缓存。

UI 收到决定后立即移除待处理项；结果幂等缓存不在 UI。

## 7. 独立确认窗口

`CastTakeoverWindow.qml`：

- 独立 top-level，不设置 `transientParent`；
- 不拉起或激活 MainWindow；
- 只显示关闭按钮；
- 右上角关闭等于拒绝；
- 显示协议、设备、媒体标题和倒计时；
- 自己 `raise/requestActivate`；
- 所有动态文本使用纯文本。

`MCast.Ui.exe --confirmation-only` 不显示主窗口、不连接 PlaybackPipe、不启动 MPV，
关闭确认窗口后退出。

当前实现：Shell 正常路径会在 UI 不存在时按需启动 confirmation-only。Shell 等待
ControlPipe 建立后转发现有确认消息；UiConfirmationBridge 在自身信号订阅完成前
暂存请求，因此不需要新增辅助窗口 ready 消息，也不会伪装主窗口 `UiFirstFrame`。

## 8. DLNA Claim 权限矩阵

DLNA 适配器不能只用“同一个 owner”或“同一个 IP”一刀切：

| 动作 | 当前权限 |
|---|---|
| 新的 `SetAVTransportURI` / 新媒体 | 必须匹配完整 peer 身份；不同 peer 进入仲裁/确认 |
| 当前 owner 同 IP 的 `Play` / `Pause` / `Seek` | 允许，兼容腾讯本地模式等身份分裂控制点 |
| `Stop` | 必须匹配完整 peer 身份；候选 Stop 只回成功，不执行 |
| `Next` / `Previous` / `SetNextAVTransportURI` / `SetPlayMode` | 必须匹配完整 peer 身份 |
| `Get*` 查询 | 不做 owner 写权限检查 |
| RenderingControl 音量/静音/画面参数 | 不做 owner 写权限检查 |
| 候选 peer 的 `Play` | 挂起，跟随候选 SetURI 确认 |
| 候选/未知 peer 的 `Stop` | 返回成功但忽略，不能停掉当前 owner |

无 User-Agent 时，如果同一地址只有一个已缓存身份，可以继承该身份；存在歧义时
不能猜测。

完整 peer 身份由来源 IP 与 User-Agent 组成。两者都相同的不同 App 在 DLNA
层不可区分，按同一控制点身份处理，不额外制造确认或判据。

同一 owner 的完全相同媒体重复 `SetAVTransportURI` 会幂等去重，不重新 Open。
同一 owner 真正换片则直接执行，不弹确认。

## 9. 所有权与迟到命令

DLNA Claim、Session 和 Runtime 必须同时守住：

```text
sessionId
ownerEpoch
mediaGeneration
operationId / HTTP requestId
```

- 迟到的 Open、Play、Stop、Seek 不能穿过新媒体边界；
- 旧 owner 的 completion 不能覆盖新 owner；
- 旧 HTTP completion 不能完成新一代请求；
- candidate 命令在确认前不能操作旧 owner；
- 只有授权后才把 owner epoch 带到实际提交动作。

这些不是可选优化，而是防止“新投送已开始，旧请求又把状态拖回去”的硬约束。

## 10. 超时层级

| 阶段 | 当前上限 |
|---|---:|
| PlaybackPipe 普通命令等待/写入 | 5 秒 |
| 媒体规划/预读 | 8 秒 |
| Claim operation 到媒体打开完成 | 10 秒 |
| UI 媒体加载 watchdog | 10 秒 |
| Session Open | 20 秒 |
| HTTP Pending 网络层兜底 | 60 秒 |
| 主动断开总 deadline | 8 秒 |

这些不是同一层超时。Claim 拒绝或超时必须主动完成对应 HTTP，不能把它挂到 60 秒
网络兜底；主动断开即使 EndSession/GENA 卡住，也必须在 8 秒总 deadline 内收口。

## 11. 当前实现边界

已实现：

- Qt-free `CastArbiter` 和 `CastClaimCoordinator`；
- 首次 Claim、禁止/立即/确认抢占、拒绝、超时和重复 Claim；
- DLNA `SetAVTransportURI -> Play` 的真实异步 Claim 接入；
- 同 owner 换片、不同控制点确认、候选命令隔离；
- Protocol↔Shell↔UI 确认请求、决定和取消；
- 独立 QML 确认窗口和 `--confirmation-only` 手工模式；
- Shell 双 generation、32 项结果缓存和 fail-closed；
- Shell 无 Ui 时的 confirmation-only 冷启动；
- 确认允许后 confirmation-only -> Normal Ui 的唯一 Ui 切换；
- owner epoch 到实际媒体提交的校验。

尚未完成：

- 仲裁策略持久化和设置页；
- “投送中隐藏发现”；
- `sessionRetired` 的真实 DLNA 生产调用和协议级旧会话 goodbye；
- Google Cast / AirPlay / Miracast Claim 适配器；
- 真实控制点对确认窗口的等待时长专项实测。
