# 多协议投送与确认架构

最后更新：2026-11-11

本文记录多协议投送所有权、确认窗口、Shell/UI 转发和后续生产接线的技术设计。
状态转换的完整规则见 `投送仲裁状态机.md`，三进程职责见 `多进程架构.md`。

## 1. 目标

同一时刻只有一个投送所有者。DLNA、Google Cast、AirPlay、Miracast 和厂商协议
都只能通过一个中性 Claim 竞争所有权。

确认窗口属于 UI，不属于 Shell，也不属于具体协议：

- Shell 不解析 SOAP、Cast 或 AirPlay 报文。
- Protocol 不创建 Qt 窗口。
- UI 不判断协议动作是否合法，只显示 Shell 转来的待确认 Claim。
- 用户确认前，旧投送继续播放，所有者与 epoch 不变。
- 用户拒绝、关闭窗口或超时，旧投送完全不受影响。

## 2. 当前进程与窗口关系

```text
MCast.Shell.exe
  ├─ ControlPipe
  │    ├─ MCast.Protocol.exe   网络会话、Claim、仲裁
  │    └─ MCast.Ui.exe         Qt/QML、主窗口和辅助窗口
  │
  └─ PlaybackPipe
       ├─ MCast.Protocol.exe
       └─ MCast.Ui.exe
```

窗口只在 `MCast.Ui.exe` 内创建：

- `MainWindow.qml`：主窗口，只在需要时创建。
- `PictureWindow.qml`：显示效果窗口，是主窗口的 owned window。
- `CastTakeoverWindow.qml`：投送确认窗口，是独立 top-level window，
  不设置 `transientParent`，不拉起或激活主窗口。

所有窗口共享同一个 UI 进程、Qt 应用对象和 `QQmlApplicationEngine`。不会为
确认窗口另起一个 Qt 进程。

### 启动顺序

- 没有 UI 窗口：`MCast.Ui.exe` 可以不存在。
- 任意 UI 窗口需要显示：Shell 启动唯一的 `MCast.Ui.exe`。
- 主窗口先出现，确认窗口后出现：两者在同一 UI 进程。
- 同一宿主架构允许确认窗口先出现、主窗口后出现；但当前
  `--confirmation-only` 模式只等待确认窗口，之后不会自行切换成 MainWindow。
- 当前普通 UI 在 MainWindow 关闭时退出；confirmation-only 在确认窗口关闭时退出。
  “最后一个窗口关闭才退出”是以后增加更多长期辅助窗口时需要细化的生命周期策略。

`--confirmation-only` 是当前提供的确认专用 UI 模式：

- 不显示主窗口；
- 不连接 PlaybackPipe；
- 不启动 mpv；
- 确认窗口关闭后 UI 进程退出。

目前 Shell 的正常启动链尚未按需选择该模式；它先在手工/测试路径中验证架构。

确认专用模式当前不上报 `UiFirstFrame`，因此还不能直接套用普通
`UiActivateRequest -> FirstFrame -> 淡出启动屏幕`的生命周期。后续若 Shell 改为
按需启动它，需要单独的 “auxiliary ready/first frame” 信号，不能复用主窗口
首帧看门狗。

## 3. 权威状态

`CastArbiter` 位于 Protocol 进程，是投送所有权的唯一权威：

```text
owner
ownerSessionId
sessionEpoch
phase
pendingClaim
retiringSessions
stateRevision
```

关键不变量：

1. 最多一个 owner。
2. 最多一个 pending claim。
3. 只有所有权真正改变时才递增 `sessionEpoch`。
4. pending 出现或消失可以改变 `stateRevision`，但不改变 owner 和 epoch。
5. 旧 session 迟到的事件按 session ID 丢弃。
6. 确认前的旧投送不能被结束。
7. 确认、拒绝和超时都必须落到同一个终止状态。

`CastClaimCoordinator` 只对第一次进入 `ConfirmationRequired` 的 Claim 产生
`ConfirmationPrompt`。相同 `(protocol, claimId)` 的重传返回 duplicate，调用方应
继续等待已有确认，不能再发一条 UI 请求。

Coordinator 要求 Protocol 内单一仲裁执行上下文串行调用 `claim/resolve/tick`，
所有 `CastTime now` 都来自同一个 steady clock 起点。`ConfirmationPrompt` 保存
Arbiter 的绝对 deadline 和一个 remaining 快照；真正写 IPC 前应使用同一时钟重新
计算 remaining。

## 4. 确认消息链

### Protocol → Shell

消息：`CastConfirmationRequest`

```text
protocol
claimId
peerId
peerDisplayName
peerAddress
mediaTitle
remainingTimeoutMs
```

消息方向固定为 `Protocol -> Shell`，走 ControlPipe。IPC 最低 minor 为 `1`。

### Shell → UI

消息：`UiCastConfirmationRequest`

```text
与 Protocol 请求相同的中性字段
messageId       Shell 生成，UI decision 回传时作为 correlationId
correlationId   原 Protocol 请求的 messageId
```

消息方向固定为 `Shell -> UI`，IPC 最低 minor 为 `2`。

### UI → Shell

消息：`UiCastConfirmationDecision`

```text
protocol
claimId
accepted
```

消息方向固定为 `UI -> Shell`。`correlationId` 必须等于对应
`UiCastConfirmationRequest.messageId`。

### Shell → UI 取消

消息：`UiCastConfirmationCancel`

无 payload；`correlationId` 指向要关闭的 UI 请求。用于：

- Protocol 连接断开或换代；
- UI 连接换代；
- 确认 deadline 已到；
- Shell 正在退出。

### Shell → Protocol 决定

消息：`CastConfirmationDecision`

字段与 UI decision 相同，方向固定为 `Shell -> Protocol`。

### Protocol → Shell 取消

消息：`CastConfirmationCancel`

- 无 payload；
- 方向固定为 `Protocol -> Shell`；
- `correlationId` 等于原 `CastConfirmationRequest.messageId`。

Shell 收到后唤醒对应等待者、取消 UI 请求窗口，并且不向 Protocol 发送
`CastConfirmationDecision`。取消早于 Shell 登记 pending 时也必须记住该请求 ID，
避免后续异步登记出一个无人接收结果的窗口。

### PlaybackPipe 重连

`PlaybackReconnectRequest`（`Protocol -> Shell`）由 Shell 转成
`UiPlaybackReconnect`（`Shell -> Ui`）。UI 收到后用同一 activation ID、nonce
和已有 Protocol identity grant 重新连接 PlaybackPipe；Protocol 在发送通知前
已经重新启动同一条 PlaybackPipe listener。UI 进程、窗口和 mpv 都不重启。

候选在确认前还没有 session 所有权，因此确认相关消息的 `sessionId` 和
`stateVersion` 固定为 `0`。decision 只有 `accepted`，不区分拒绝、超时、窗口
创建失败或取消；这些差异由 Shell/UI 日志表达，仲裁语义统一为 fail-closed。

## 5. 时序

### 用户允许接管

```text
Protocol
  -> CastArbiter::claim(AirPlay)
  -> AwaitingConfirmation
  -> CastConfirmationRequest
Shell
  -> UiCastConfirmationRequest
UI
  -> CastTakeoverWindow.qml
  -> 用户点击「允许投送」
  -> UiCastConfirmationDecision(accepted=true)
Shell
  -> CastConfirmationDecision(accepted=true)
Protocol
  -> CastArbiter::confirmPending(true)
  -> 新 owner / epoch + 1
  -> 旧 session SessionEnded(Preempted)
  -> 新 session Preparing
```

### 用户拒绝、关闭窗口或超时

```text
用户点击「继续当前投送」
或点击右上角关闭
或 QML 倒计时到 0
  -> UiCastConfirmationDecision(accepted=false)
  -> Shell -> Protocol
  -> CastArbiter::confirmPending(false)
  -> pendingClaim 清除
  -> 旧 owner / epoch 完全不变
```

### UI 不可用

```text
Protocol claim -> AwaitingConfirmation
Shell 找不到 UI Control 连接
  -> 立即返回拒绝
Protocol 保持旧 owner
```

不能因为确认窗口不可用而错误接受新投送。

## 6. Shell 的连接代次

Shell 分开维护两个单调 generation：

### `protocolGeneration`

- Protocol Control 连接注册或当前连接清除时递增。
- 绑定到 Protocol worker。
- Protocol 重连取消旧 pending claim 和缓存。

### `uiGeneration`

- UI Control 连接注册或当前连接清除时递增。
- 与 `m_uiControlConnection` 在同一把锁下发布。
- 每个 pending 保存创建它时的 UI 连接和 UI generation。
- UI decision 必须来自同一连接、同一 generation。
- UI 重连只取消旧 generation 的 pending，不取消刚发到新 UI 的请求。
- 取消消息通过 pending 保存的原 UI 连接发送，不能发给后来注册的连接。

UI 连接只有在 `PeerIdentityGrant` 成功写入后才对确认转发可见，避免 grant 和确认
请求争抢 ControlPipe 的先后顺序。

Shell 的最近确认结果缓存只保留 32 项，键为
`请求 messageId + protocol + claimId`，并绑定 `protocolGeneration`；Protocol
或 UI 连接换代时清空。当前 owner、pending 和最近决定不依赖无限期保留旧消息 ID。

## 7. UI 进程与线程

```text
UiConfirmationBridge reader thread
  -> decode ControlPipe
  -> emit requestReceived
  -> queued connection to UI main thread

UI main thread
  -> MainWindow::showCastConfirmation
  -> create CastTakeoverWindow.qml
  -> user action
  -> MainWindow::respondCastConfirmation
  -> UiConfirmationBridge submits decision
```

约束：

- QML 和 `QQuickWindow` 只能在 UI 主线程操作。
- Control reader 不直接调用 QML。
- Shell 不在 UI 进程内持有窗口指针。
- 主窗口不是确认窗口的 owner；Windows 不会因主窗口最小化而隐式隐藏确认窗口。
- 确认窗口自己 `raise/requestActivate`，不调用主窗口的 `show/raise`。

### ControlPipe 生命周期与首帧

- UI ControlPipe 现在跨整个 UI 生命周期保持，Shell 的读取超时为 `24h`；
  不再把首帧当成“ControlPipe 可以关闭”的标志。
- 普通 MainWindow 的首帧仍由 `UiFirstFrame` 上报，但发送职责已经移到
  `UiConfirmationBridge`，因为 Control 连接由该 bridge 长期持有。
- UI 进程退出通过 ControlPipe 断开感知，不依赖固定空闲超时。

## 8. QML 窗口行为

`CastTakeoverWindow.qml`：

- `FluWindow`，固定尺寸；
- `showMinimize: false`；
- `showMaximize: false`；
- `showClose: true`；
- `stayTop: true`；
- 不设置 `transientParent`；
- 使用 `MicaBackdrop`；
- 显示协议、设备、媒体标题和倒计时；
- 默认按钮是「继续当前投送」；
- 关闭按钮映射 `accepted=false`；
- 允许按钮映射 `accepted=true`；
- 所有动态文本 `Text.PlainText`。

IPC 层拒绝：

- 非法 UTF-8；
- NUL；
- C0/C1 控制字符；
- 主要 Unicode bidi 控制符；
- 换行和行分隔符；
- 超长设备名、地址和标题。

## 9. 失败矩阵

| 故障 | 结果 |
|---|---|
| 用户点允许 | accepted=true |
| 用户点继续当前投送 | accepted=false |
| 点右上角关闭 | accepted=false |
| UI 倒计时结束 | accepted=false |
| QML 窗口创建失败 | accepted=false |
| UI Control 不存在 | accepted=false |
| UI Control 在确认期间断开 | 取消 waiter，accepted=false |
| Protocol 取消确认 | 唤醒 Shell waiter、关闭 UI 窗口、不回 decision |
| Protocol Control 换代 | 取消 UI 窗口，accepted=false |
| Shell 退出 | 取消 pending waiter 和 UI 窗口 |
| UI decision correlation 不匹配 | 忽略 |
| UI decision 来自旧连接或旧 generation | 忽略 |
| decision 的 protocol/claimId 不匹配 | 忽略 |
| 消息 minor 低于要求 | schema 拒绝 |

所有失败路径都是 fail-closed：旧投送继续，绝不让候选在未确认时取得所有权。

## 10. 当前实现边界

已完成：

- `CastArbiter` 纯状态机；
- `CastClaimCoordinator`：Protocol 侧唯一仲裁入口，负责把
  `AwaitingConfirmation` 转成中性确认提示；
- Protocol ↔ Shell 确认消息；
- Shell ↔ UI 确认请求、决定和取消；
- UI 独立 QML 确认窗口；
- Shell 双 generation、pending、deadline 和结果缓存；
- confirmation-only UI 模式；
- 真实 DLNA Claim 所需的异步 Pending HTTP、来源 IP 与 requestId；
- DLNA 协议内 `DlnaClaimAdapter`：首投、同 owner 换片、确认、拒绝、超时、
  重复决定和候选命令隔离；
- Protocol ControlPipe 单 reader dispatcher：UI activation、投送确认、唯一消息
  ID、terminal fail-closed 和重复响应隔离；
- `DlnaClaimRuntime`：HTTP requestId 与待确认/慢 Open 事务关联，媒体就绪后才
  完成 SetURI/Play；
- `DlnaClaimHttpHandler`：复用 SoapRouter 校验，异步接管 SetURI/Play/Stop，
  串行化授权与 callback，并给慢 Open 设置 10 秒 deadline；
- `DlnaHttpFrontend`：设备描述、三份 SCPD 和 SOAP POST 的统一 HTTP 入口；
- `DlnaClaimConfirmationWorker`：在 HTTP 线程之外等待中性确认结果：
- `DlnaProtocolRuntime`：组合 HTTP、SoapRouter、Claim、确认 worker 和播放任务
  线程，Protocol 可在 Ui 缺席时持续运行；
- `LateBindingPlaybackGateway`：Ui 缺席时失败关闭，PlaybackPipe 出现/退出时
  挂接和卸下真实播放网关；
- `ProtocolDlnaConfirmationPort`：把中性 ConfirmationPrompt 映射到 ControlPipe，
  并支持取消；
- ControlPipe 的确认请求由 Shell 异步等待，读线程继续接收
  `CastConfirmationCancel`；
- PlaybackPipe 单边断开后由 Protocol 发起、经 Shell 转发，UI 原进程重新挂接；
- 两个手动烟测入口：
  - 原生 Task Dialog：`mcast_cast_confirmation_dialog_smoke`；
  - QML 独立窗口：
    `MCast.Ui.exe --standalone --confirmation-only --test-takeover-window`。

尚未完成：

- SSDP/GENA 尚未迁入 `DlnaProtocolRuntime`；
- “暂停接收”尚未驱动 Runtime 的 HTTP/表面启停；
- Google Cast / AirPlay / Miracast 的 Claim 适配器；
- Shell 在 UI 不存在时按需启动 confirmation-only UI；
- 确认策略的持久化配置与设置页开关；
- “投送中隐藏发现”；
- UI 与 Shell 共享同一个单调时钟 deadline；当前 UI 使用收到的剩余毫秒重新
  建立本地倒计时，真实仲裁 deadline 仍以 Shell 为准；
- 真实控制点等待确认时长的单独实测。

## 11. 下一步顺序

1. 在 Protocol 实例中持有唯一 `CastClaimCoordinator`，并由它统一接入
   `CastArbiter`。
2. 将 DLNA 的明确换片/播放请求翻译成中性 Claim；订阅、发现、状态查询不算 Claim。
   `DlnaClaimAdapter` 已完成纯协议状态层，尚待 runtime 接入 socket 与 IPC。
3. 当 `claim()` 返回 `AwaitingConfirmation` 且 `confirmation.has_value()` 时，
   从 Protocol 发送 `CastConfirmationRequest`，在 ControlPipe 上等待决定；
   duplicate pending 只等待已有确认，不再发送 UI 请求。
4. 决定到达后调用 `CastArbiter::confirmPending()`；只有 accepted=true 才进入
   `Handoff`。
5. 接入旧 session 的协议级结束/再见，先让新 owner 进入 Preparing，再接 UI 和
   Playback。
6. 增加真实 DLNA 控制点的等待时长测试，再确定生产确认超时。
7. 最后接设置持久化、按需启动 confirmation-only UI 和 Google Cast/AirPlay。

在步骤 3–5 完成前，不能宣称生产环境已经能由真实手机投送触发确认窗口。
