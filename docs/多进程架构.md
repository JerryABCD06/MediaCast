# Media Cast 多进程架构

更新日期：2026-11-12

本文只记录当前生产实现和不可腐蚀的边界。重构过程见
[history/多进程重构交接-2026-11-12.md](history/多进程重构交接-2026-11-12.md)。

## 1. 生产进程

| 代号 | 进程 | 当前职责 |
|---|---|---|
| A | `MCast.Protocol.exe` | 无 Qt；SSDP、HTTP、SOAP、GENA、DLNA 会话、Claim、媒体规划 |
| B | `MCast.Ui.exe` | Qt/QML、FluentUI、libmpv、元数据过滤、实际播放测量、SMTC |
| C | `MCast.Shell.exe` | 无 Qt；托盘、启动屏幕、单实例、持久配置、语言包和子进程启动 |

硬约束：

- A 和 C 不链接 Qt。
- 没有 UI 窗口时，B 进程不存在；Qt/QML/OpenGL/libmpv 均不驻留。
- A 不直接启动 B，只向 C 发 `UiActivateRequest`。
- C 是唯一启动 A/B 的进程。
- A 是网络会话、媒体队列和逻辑 transport 状态权威。
- B 是实际 position/duration/buffer/volume/mute 和渲染权威。
- C 是持久配置、语言选择和进程状态权威。
- 协议专属 DIDL、SOAP 动作名、SSDP 头和 GENA 细节不能穿过 A。

`src/skeleton/` 不是纯测试目录。`MCast.Protocol` 的生产入口和真实 DLNA Runtime
都在这里；`MCast.UiSkeleton` 才只是 `BUILD_TESTING` 下的无 Qt 测试替身。

## 2. 真实生命周期

```text
双击 Shell
  -> 单实例 mutex
  -> 读取 MediaCast.json / 语言包
  -> 创建 Job Object、ControlPipe、托盘
  -> 启动 Protocol
  -> Protocol 启动 DLNA Runtime、命令管道和 ControlPipe 心跳

普通启动
  -> Shell 启动 Protocol 时附带 --request-ui
  -> Protocol 发 UiActivateRequest
  -> Shell 显示启动屏幕并启动 Ui

托盘打开 / 二次启动
  -> Shell 向 Protocol 发 UiOpenRequest
  -> Protocol 等待 Playback/Ui 激活前置条件就绪
  -> Protocol 再发 UiActivateRequest
  -> Shell 显示启动屏幕并启动 Ui

共同后续
  -> Ui 完成 Control Hello、语言/设置快照、Protocol identity grant
  -> Ui 连接 PlaybackPipe 并请求 SessionSnapshot
  -> 创建 MainWindow
  -> frameSwapped 后 UiFirstFrame
  -> Shell 淡出启动屏幕

手机首次投送
  -> Protocol 先 probeOnly 查询 UI 是否存在
  -> 不存在则发真实 UiActivateRequest
  -> 后续链同上
```

`--background` 仍启动完整 Protocol 和托盘，只是不主动请求 UI。

首帧和播放就绪是两个门：

- 隐藏启动屏幕只等 QML 首帧 `UiFirstFrame`；
- 放行媒体命令还要等窗口首帧、MPV render context 和 PlaybackBridge 三者都就绪，
  由 `PlaybackUiReady` 表达。

UI 首帧看门狗当前为 15 秒。超时后 Shell 隐藏启动屏幕、终止 UI、清理记录，并允许
下一次激活；Shell 继续运行。

## 3. 四类命名管道

| 管道 | 用途 | 当前保护 |
|---|---|---|
| `MediaCast.Control.<SID>.<instance>` | Hello、设置、语言、UI 激活、确认、首帧 | Hello/HelloAck；PID、nonce、build ID、角色和方向校验 |
| `MediaCast.Playback.<SID>.<instance>` | 播放命令、快照、状态和断开请求 | Hello/HelloAck；UI 校验 Protocol PID、EXE 哈希和 Shell grant |
| `MediaCast.ProtocolCommands.<SID>.<instance>` | Shell 修改接收/广播运行态 | 每次新建连接；同用户 ACL，校验对端 PID 和 Shell 持有的 EXE 哈希 |
| `MediaCast.ShellCommands.<SID>.<instance>` | 第二次启动移交给已运行 Shell | 专用交接协议；校验旧 Shell 身份/EXE 哈希 |

不是所有管道都走同一套 Hello。文档不能笼统写成“所有连接都做完整双向哈希认证”。

Shell nonce 每次 Shell 启动生成一次，供本次实例的 A/B 和连接使用；它不是每条
消息一次性 token。Control 上 UI 校验 Shell PID 和 nonce；EXE 哈希主要用于 Shell
校验子进程、UI 校验 Protocol，以及二次启动交接。

## 4. IPC 帧与版本

当前帧协议为 **1.4**。帧头固定 64 字节，payload 使用 TLV：

- 单帧 payload 最大 1 MiB；
- 最多 64 个字段；
- 单字段最大 256 KiB；
- 未知字段可忽略，重复字段非法；
- 新消息声明最低 minor；高于本机的 minor 直接拒绝；
- 当前子进程仍要求同一次构建，不支持跨 minor 混跑。

关键消息：

- Control：Hello、设置快照/patch、语言目录、`UiActivateRequest`、
  `UiFirstFrame`、确认请求/决定/取消、Playback 重连通知；
- Playback：Hello、`SessionSnapshot`、播放命令/完成、状态增量、
  `PlaybackUiReady`、`UiEndCastRequest`。

当前心跳实际是 Protocol 每秒向 Shell 写 `Heartbeat` 的单向保活；Shell 不发送
`HeartbeatAck`。真正检测 Control 丢失主要靠读超时/连接关闭，而不是双向心跳超时。

## 5. 播放数据面

`PlaybackPipe` 同时承担命令、快照和遥测：

- 状态快照 latest-wins；
- 同一 generation 下，未发送的 Play/Pause、绝对 Seek、Volume、Mute 和同名画面
  参数按属性合并；
- Open、Stop、Next、Previous、SetNext、SetPlayMode 是顺序边界，不能互相覆盖；
- EndSession/断开清空尚未发送的普通命令；
- 被合并的 command ID 通过 alias 向所有等待者回填结果；
- 写入中的命令不会因超时被随意取消；
- position 等高频遥测不无界排队。

`UiEndCastRequest` 走优先通道，避免媒体命令风暴把“断开”堵在普通队列末尾。

## 6. 状态所有权

| 状态 | 唯一权威 |
|---|---|
| 语言、主题、强调色、Mica、广播、接收、画面恢复值 | Shell |
| 设备名称、UDN | Shell 持久化；Protocol 使用，UI 显示快照 |
| SSDP/HTTP/SOAP/GENA 会话和订阅 | Protocol |
| 当前媒体、历史/下一条、播放模式 | Protocol |
| 逻辑 transport 状态 | Protocol（由 UI 事实驱动） |
| 当前 owner、待确认候选、退场记录 | Protocol 内的 `CastArbiter` |
| 实际 position/duration/buffer/volume/mute | UI |
| QML 引擎、窗口、渲染、SMTC 宿主 | UI |
| 进程启动/停止现状 | Shell |

Shell 的设置版本、ReceivingState version 和 Playback `stateVersion` 是三个独立版本
域，不能互换。设置版本是进程内版本，不持久化到磁盘。

## 7. 当前故障矩阵

| 异常 | 已实现行为 | 尚未实现 |
|---|---|---|
| A 崩溃 | B 因 ControlPipe 丢失退出；Shell 清除 A 连接 | Shell 自动重启 A、向 B 发送明确会话结束 |
| B 崩溃 | Shell 清理 UI 和启动屏幕；下一次激活可启动新 B | 立即自动重启、向控制点返回明确失败 |
| C 崩溃 | Job 的 `KILL_ON_JOB_CLOSE` 一起结束 A/B | A 反向拉起 Shell |
| 仅 PlaybackPipe 断开 | A 重建 listener，经 C 通知 B 重连；窗口/MPV 不重建 | 更完整的故障预算和长稳 |
| A 内部网络面失败 | Runtime 可重建 HTTP/SSDP/GENA | 这不是进程重启，不能混写 |

`RestartController` 和退避预算已经作为纯逻辑实现并有测试，但还没有在
`ShellMain.cpp` 生产路径中实例化。目标语义不能写进“当前已实现”列。

## 8. 确认专用 UI

`MCast.Ui.exe --confirmation-only` 已能显示独立确认窗口，但不连接 PlaybackPipe、
不启动 MPV、关闭窗口后退出，也不上报 MainWindow 首帧。

当前 Shell 尚未在“主窗口不存在但需要确认”时按需启动这个模式。没有现成 UI
Control 连接时，确认请求 fail-closed。后续接入需要独立的辅助窗口 ready 信号，
不能复用 `UiActivateRequest -> UiFirstFrame` 主窗口看门狗。

## 9. 设计纪律

- 新代码使用 `MainWindow` / `mainWindow`，不再出现 `NewUi`。
- QML 和窗口只在 UI 主线程操作。
- A/B/C 的规则变化先更新本文，再改实现。
- 任何“目标上应该如此”与“代码已经如此”必须分栏写。
- 改头文件后 clean-first；每次较大改动跑测试并做静态复审。
