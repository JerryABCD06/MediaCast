# Media Cast 多进程架构

最后更新：2026-11-11

这份文档记录 A/B/C 三进程重构的硬约束、状态所有权和通信规则。实现可以分阶段
迁移，但下面的边界不能靠“暂时先这样”慢慢腐蚀。

当前实现进度、准确唤起时序、构建命令和下一步顺序见
`多进程重构交接.md`。

## 1. 三进程

| 代号 | 进程 | 职责 |
|---|---|---|
| A | `MCast.Protocol.exe` | SSDP、HTTP、SOAP、GENA、设备发现、网络会话和逻辑传输状态 |
| B | `MCast.Ui.exe` | Qt/QML、`MainWindow`、libmpv、实际播放测量和画面渲染 |
| C | `MCast.Shell.exe` | 原生托盘、启动屏幕、单实例、配置、SMTC、进程监督 |

硬约束：

- A 和 C 不链接 Qt。
- 未打开 `MainWindow` 时，B 进程不存在，Qt/QML/OpenGL/libmpv 均不驻留。
- A 不直接启动 B。A 只能向 C 发 `UiActivateRequest`。
- C 是唯一有权启动、停止和重启 A/B 的进程。
- A 是网络会话权威；B 是实际播放测量权威；C 是持久配置和进程状态权威。
- 高频播放遥测走 A ↔ B，不经过 C。

## 2. 状态所有权

| 状态 | 唯一权威 | 说明 |
|---|---|---|
| 语言包、语言选择、主题、Mica、广播、接收、画面参数 | C | Shell 扫描语言包并原子写 JSON；B 拿 LanguageCatalog 与 SettingsSnapshot |
| 设备名称、设备 UDN | C 持久化，A 使用 | B 从快照显示，A 重启后身份不变化 |
| SSDP/HTTP/GENA 会话和订阅 | A | B 不解析 DLNA |
| 当前媒体、队列、播放模式 | A | B 只播放 A 指定的单条媒体 |
| 逻辑 transport state | A | B 上报事实，A 维护状态机 |
| 当前投送所有者、待确认候选、退场记录 | A | 统一由 `CastArbiter` 维护，其他模块只读快照 |
| 实际 position/duration/buffer | B | A 缓存带时间戳的协议视图 |
| 实际 volume/mute | B | A 缓存并转换成 RenderingControl 等协议值 |
| QML 引擎、窗口、实际渲染 | B | B 退出即全部释放 |
| SMTC 对象和宿主 HWND | C | 命令先到 A，再由 A 发给 B |
| 进程启动/停止/重启状态 | C | A/B 只能报告自身状态 |

“缓存”不是第二份权威。A 保存播放快照是为了回答 SOAP/GENA；不能让 A 和 B
各自维护一份当前媒体或队列。

多协议抢占的完整状态和转换规则见 `投送仲裁状态机.md`。核心约束是：任何时刻最多
一个 owner；确认前旧 owner 不变；只有用户确认后才递增所有权 epoch；旧协议退场
与新协议准备可以并行，但旧会话不能再修改中央状态。

确认窗口、Shell/UI 双 generation、IPC 消息和后续 Claim 接线顺序见
`多协议投送与确认架构.md`。

## 3. 打开主窗口

```text
手机请求
  -> A 校验请求、协议、URI、会话
  -> A 向 C 发送 UiActivateRequest(request_id, session_id, deadline)
  -> C 立即显示启动屏幕
  -> C 启动 B
  -> B 连接 A 的 PlaybackPipe
  -> B 发送 Hello + SessionSnapshotRequest
  -> A 返回当前会话快照
  -> B 创建 MainWindow、加载媒体
  -> B 向 C 报告 FirstFrame
  -> C 收到 FirstFrame 后淡出启动屏幕
```

必须满足：

- `UiActivateRequest` 幂等。重复请求按 `request_id`/`session_id` 合并。
- `UiStarting` 状态下再来请求只强化启动屏幕，不再启动第二个 B。
- SOAP 响应不能同步等待 QML 创建、首帧或 `grabWindow()`。
- B 启动失败、崩溃或超时，网络进程仍要存活，并向控制点返回明确错误。
- 启动屏幕只归 C，不依赖 B 是否已完成 QML 初始化。

## 4. IPC

使用当前用户 ACL 保护的 Windows Named Pipe：

- `\\.\pipe\MediaCast.Control.<SID>.<instance>`
- `\\.\pipe\MediaCast.Playback.<SID>.<instance>`
- `\\.\pipe\MediaCast.ProtocolCommands.<SID>.<instance>`
- `\\.\pipe\MediaCast.ShellCommands.<SID>.<instance>`

帧格式固定为：

```text
magic + 版本 + 消息类型 + 源/目标角色 + flags
+ message_id + correlation_id + session_id + state_version + timestamp
+ payload_size + payload
```

规则：

- payload 有硬上限，字段使用 TLV，未知字段可忽略，重复字段非法。
- Hello 必须包含角色、PID、实例 nonce、构建版本和能力集。
- C 校验客户端 PID、当前用户、实例 nonce 和构建版本。
- 每条命令有 message ID；重试保持 ID，接收方负责幂等去重。
- 快照带 `state_version`；重连后先取 Snapshot，再接收更高版本事件。
- IPC minor 只增不减；新消息必须声明最低 minor。帧层拒绝高于本机的 minor，
  当前子进程仍要求同一次构建，不支持跨 minor 混跑。
- position 遥测采用 latest-wins，不允许无界排队。
- 握手、命令、首帧、心跳都有明确超时。
- 日志每行包含进程角色、实例、会话、message ID 和 correlation ID。

## 5. 崩溃监督

| 异常 | 感知者 | 处理 |
|---|---|---|
| A 崩溃 | C、B | C 标记协议不可用，B 结束当前播放；C 按预算重启 A |
| B 崩溃 | C、A | C 清理启动屏幕和残留；A 标记会话失败；有限次自动重启 |
| C 崩溃 | A、B | B 直接退出以卸载 Qt；A 暂停接受新请求并重启 C |

唯一一条反向监督是 **A 重启 C**。B 不重启 C，避免两个进程同时拉起多个 Shell。

重启必须使用：

- 单实例 mutex；
- 实例 nonce；
- 指数退避；
- 稳定运行后清零的崩溃预算；
- 超过预算后停止自动拉起并写原始日志。

## 6. DLNA 抽象边界

协议层对外只发送中性类型，例如：

- `CastRequested(MediaDescriptor)`
- `SessionEnded(reason)`
- `TransportCommandReceived(command)`
- `SeekRequested(positionMs)`
- `VolumeCommand(level, muted)`
- `PictureControlChanged(control)`
- `PlaylistChanged(items, current)`
- `PeerPresenceChanged(connected)`

以下内容不能越过 A 的边界：

- `AvTransport` / `RenderingControl` 等 SOAP 动作名；
- DIDL-Lite 节点；
- UPnP class；
- SSDP header；
- GENA 的 SEQ/回调地址；
- 原始 XML。

未来接入 Google Cast 或 AirPlay 时，B 的主窗口和播放器不应新增 DLNA 条件分支。

## 7. 命名

新代码统一使用 `MainWindow` / `mainWindow`，QML 根文件名为
`MainWindow.qml`。旧的 `NewUi` 称呼已经从当前代码、资源和文档中移除。

纯改名与行为重构分开提交，避免破坏 review 和回滚。

## 8. 分阶段验收

| 阶段 | 验收 |
|---|---|
| IPC 基础 | 帧、长度、版本、TLV、损坏输入和命名管道测试通过 |
| 三进程骨架 | A/B/C 可启动握手；强杀任一进程有确定恢复行为 |
| B 抽取 | 关闭 MainWindow 后 B、Qt、QML、OpenGL、libmpv 全部退出 |
| C 抽取 | `--background` 下没有任何 Qt 模块 |
| A 抽取 | 新 A 不链接 Qt；手机行为与旧实现 wire-level 一致；正式网络入口消费接收开关 |
| 投送仲裁 | 首次 Claim、保护、确认、拒绝、超时、跨协议抢占和并行退场状态机测试通过 |
| 切换 | 删除单进程旧路径，完成长稳和故障注入 |

## 9. 构建纪律

改过任何 `.h` 后必须删除整个构建目录，重新配置并全量编译。增量构建在这个
工程上已经出现过“编译链接成功、运行即崩”的历史问题。每次崩溃转储必须和时间
戳相同的 EXE/PDB/MAP 配套使用。
