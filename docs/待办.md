**最近这几轮做完的**：

- **控制栏的显隐规则**（`components/MediaBar.qml` 顶部那段注释是权威）：
  空闲 / 放音乐**常显**；视频**在放**时鼠标进下沿那条热区就显示、挪开立刻收；
  视频暂停 / 放图片算"静止画面"——鼠标在整个画面框里动一下就显示，停手或挪到
  窗口外 3 秒后收；**刚投上来的视频**先露 5 秒（那 5 秒里不管鼠标在哪），
  图片没有这 5 秒。两条兜底：鼠标停在栏自己身上时不收；播放↔暂停切换时规则直接换。
- **全屏**：媒体栏右端那个键 + **双击画面** + **Esc** 退出。全屏 = 无边框铺满
  （标题栏隐去、内容区吃掉顶栏那 48 像素）；退出**原样返回**——普通窗口回普通、
  最大化回最大化，位置尺寸都不变。一个事实 + 一张表 + 一处执行的写法见
  `NewUiWindow.qml` 里那段。
- **云母底改成自己画**（`components/MicaBackdrop.qml`）。以前的分工是"窗口透明、
  页面跟着透"，于是每个要挡住下层内容的页面都得配一份"我底下压着什么、它要不要
  收起来"的知识 —— 加一页就多想一层。现在反过来：**谁要底谁摆一块实心的**，
  关掉开关就是那块 #F3F3F3；系统云母那行 `effect: "mica"` 还留着，但被盖住了。

  **分两步：造一次，各处只裁。** 造的那一层全窗口只有一处（窗口背景，`isSource`
  —— 它不在被裁剪的内容区里，这一点很要紧）；它把**整块屏幕那么大**的云母
  （壁纸模糊 + 染色 + 噪点）算好、钉在屏幕坐标系上。别处的底一律从这张图上裁
  自己那一格（`ShaderEffectSource` 取像素），**不重算**。

  为什么非要这样：一开始是"每块底各算各的"，接缝上会偶尔冒出一道淡淡的横线 ——
  模糊里的噪点层是按各自左上角平铺的，两块算出来差两三个色阶。而且窗口一动、
  页一换就得重算。现在**所有底都来自同一张图的同一批像素**，接缝在结构上不可能
  存在；窗口移动缩放只改"裁哪儿"，不动那张图。逐点比对过：设置页和投屏页在
  同一坐标上差 0。
- **状态机收尾**：片子自然播完、换下一条、加载期间按停止 —— 三种情况的状态
  都对得上了（前两个的坑在 keep-open，第三个是"加载好了"把停止顶回去）。
- **无文字的按钮都有悬停提示**：方向按位置挑 —— 顶栏和窗口三键往下弹，
  压在画面下沿的控制栏往上弹。

### 3. 发布目录整理

**能打包了**，两条命令：

1. `work\configure-mcast-release.ps1 -Build` —— 配一个 Release 构建目录
   （`work\mcast-release`；Ninja 一个目录只能是一种构建类型，所以另开一个，
   不碰平时用的 Debug 目录）。
2. `work\deploy-mcast.ps1` —— 先在干净的暂存目录里摆好 exe + `libmpv-2.dll` +
   `lang/` + `qml/`，再让 windeployqt 往这个干净目录里补 Qt 的 DLL 和插件，
   最后整份拷到目标（默认桌面上的 `Media Cast Receiver`）。

包里的样子：`MCast.exe` + Qt 的 DLL 直接放程序根目录 + `platforms/`
`imageformats/` `iconengines/` `qml/` `styles/` `tls/` 这些插件目录 + `lang/` +
`libmpv-2.dll`。合计约 244 MB —— 其中 `libmpv-2.dll` 一份就 115 MB（ffmpeg
整个在里面）、`dxcompiler.dll` 24 MB、`opengl32sw.dll` 20 MB。

**有一处和最早定的不一样**：libmpv 没放进 `runtime/mpv/`，DLL 直接躺在 exe
旁边 —— 构建的 post-build 本来就这么拷，放到别处反而要额外加 DLL 搜索路径。
（`runtime/mpv/` 里那份 mpv.exe 是给备用的 `MpvMediaPlayer` 后端用的，不进包。）

**这些脚本有个坑**：里面是中文注释，而无 BOM 的 UTF-8 脚本用 Windows
PowerShell 5.1（`powershell -File`）跑会被按 ANSI 解码，注释能吃掉下一行代码。
在 pwsh 7 里直接 `& .\xxx.ps1` 跑就没事 —— 和以前那几个脚本一样。

**打包时最容易漏的一样东西**：windeployqt 的 `--qmldir` 得给**两处** ——
源码的 `src/ui/qml`，和暂存目录里的 `qml/`（FluentUI 那一坨）。只给前者的话，
FluentUI 里 `FluAcrylic.qml` 要的 `Qt5Compat.GraphicalEffects` 不会被带上，
而**开发机上一切正常**（Qt 安装目录里那份顶上了），打包出来一开新界面就
`module "Qt5Compat.GraphicalEffects" is not installed`，新界面干脆不出来。
现在 `deploy-mcast.ps1` 两处都给，而且部署完会把两处 QML 里 import 的模块名
全抠出来挨个在包里找一遍，缺哪个就报出来（`MediaCast` 是我们自己用 C++ 注册的，
不算，脚本里排除掉了）。

还差：安装包、快捷方式、版本号进「应用和功能」、把用不上的那几套 QML 样式
（Fusion / Imagine / Material / Universal）从包里剔掉（大概能省十几 MB）。

### 5. 源码版权头的**标准写法**（加新文件时照这个来）

每个源文件开头两行，**必须一致** —— 三处（源文件、`NOTICE.md`、发布包里的
声明）写的不一样，比不写还麻烦：

```
// SPDX-License-Identifier: GPL-3.0-or-later
// Copyright (C) 2026 Wang Yunzheng <wyz-mcast@outlook.com>
```

**注释符号按文件类型换**（内容不变，只换符号）：

| 文件 | 符号 |
|---|---|
| `.cpp` / `.h` / `.qml` / `.rc` | `//` |
| `CMakeLists.txt` | `#` |
| `.qrc`（XML） | `<!-- -->` |
| `lang/*.json` | **不加** —— JSON 没有注释语法 |
| `third_party/**` | **不加** —— 不是我们的代码 |

批量加/补的脚本：`work\add-spdx.ps1`（**幂等**，已有的会跳过；保原编码、保原换行）。
加完要重编 + 真跑一次新界面 —— 注释本身不会出问题，但万一插错位置（比如插到
`<?xml?>` 声明前面、或插进 raw string 里）就未必。

`licenses/` 目录已经建好（4 份 GPL/LGPL 全文 + FluentUI 的 MIT + 组件清单
`THIRD-PARTY-NOTICES.md`），`deploy-mcast.ps1` 会把整个目录拷进发布包。

**从二进制里查证过的许可事实**（省得下次重查）：

| 事实 | 证据（在二进制里查到的原文） |
|---|---|
| libmpv 是 **GPL**，且**不是** GPLv2-only | `mpv is distributed under the terms of the GNU General Public License Version 2 or later.` |
| 它这一份构建启用了 GPL 组件 | 特性表里有 `gpl`，并有 `dvdnav` `dvdread` `libbluray` |
| 捆进来的那些库是 **LGPLv2.1+** | 5 处 `... either version 2.1 of the License, or (at your option) any later version` |
| mpv 版本 | `mpv v0.41.0-1023-g69e63f425`（构建选项里 `-Dlibmpv=true -Ddvdnav=enabled`）|

**"v2+" 和"拒绝 v3"是两件事**：mpv 写的是"v2 或更高"，也就是**允许接收者按 v3
用**。正因为如此，我们才有权把项目定成 `GPL-3.0-or-later`。（真正"避开 v3"的项目
是写成 v2-only 的，理由通常是：不想被 FSF 未来单方面改的条款绑住 —— Linux 内核
就是这条；以及硬件厂商讨厌 §6 的反 Tivo 化条款。）

**顺带澄清一个容易混的点**：GPLv3 的专利条款（§11）保护的是"**项目参与者之间的
专利和平**"—— 由贡献者就其贡献所必需的专利授予你许可，且不得对下游主张。它
**完全不提供**来自第三方的保护：HEVC 那几个专利池的权利人从没往这个项目贡献过
代码，所以选 v2 还是 v3，对他们的许可费一分钱影响都没有。**别把 §11 当成编解码器
专利问题的解药。**

**② GPL 不只是"附一份文本"。** 分发二进制要同时给三样：许可全文、**对应源码的
获取方式**（我们没改 mpv/ffmpeg，指到上游对应版本即可）、以及修改说明（无）。
而现在桌面那份发布包**一份许可文本都没带** —— 并且本地也没有现成的可拷：
Qt 安装目录没有 `LICENSES`，`runtime/mpv` 和 `runtime/mpv-dev` 里也没有任何
许可文件。标准文本得自己去取。

**③ 第三方声明现在就做，不能"等定下来再说"。** 我们已经在分发了，包里实际有：

| 组件 | 许可 | 要做的 |
|---|---|---|
| `libmpv-2.dll`（内含 ffmpeg） | **GPL v2+** | 全文 + 源码获取方式 |
| Qt6 全部 DLL 与插件（含 Qt5Compat） | **LGPL v3** | 全文 + 版权行 + "未修改"说明 |
| FluentUI（QML 组件库） | **MIT**（zhuzichu, 2023） | 全文 + 版权行 |
| `D3Dcompiler_47` / `dxcompiler` / `dxil` / `opengl32sw` | Qt 随附的第三方 | 各自条款 |

做法：包里加一个 `licenses/` 目录，一个组件一份。**Qt 是动态链接**，这满足
LGPLv3「用户能替换库」的要求 —— **所以千万别改成静态链接**，那是另一套义务。

**④ `CODECS.md` 该分成两类写。** 现在把 AV1 和 H.265 并列，但它俩性质完全不同：

- **明确免版税**：VP8、VP9、AV1（Google 和 AOMedia 都有公开承诺）
- **有专利池**：H.264/AVC、H.265/HEVC、AAC

分开写对用户更有用，也更诚实。

**⑤ `PRIVACY.md` 可以写实，因为这事我们最清楚。**
本程序**没有遥测、不联网上报**；只监听本地端口（TCP 8200、UDP 1900），只写本地
日志；日志里会带计算机名和媒体 URL（本地文件路径）。把这些写具体比模板的空话有
价值。`LEGAL-NOTICES.md` 第 5 节（网络）同理 —— 可以补上"会把计算机名广播到局域网"，
那是用户真正该知道的事。

**⑥ 这些文件将来要挪到仓库根目录。** `LICENSE` / `NOTICE` / `CONTRIBUTING` /
`SECURITY` / `CODE_OF_CONDUCT` 按惯例放根目录，平台才会识别。现在先攒在

**⑦ 关于 H.265 —— 这是专利问题，和版权是两码事。**

- **换实现躲不掉。** 专利覆盖的是"解码/编码 HEVC 这件事"这个方法本身，所以自己写、
  换库、换语言都一样。这也意味着"我们自己不写编解码器"并不构成免责理由。
- **池子不止一个。** Access Advance（原 HEVC Advance）、Via LA（原 MPEG LA 的
  HEVC 池）、Velos Media，外加不在池里的独立权利人。所谓"拿到许可"通常要谈好几家。
- **义务落在"分发方"身上，这条最关键。** 我们现在**随包分发 libmpv**，而它里面有
  HEVC 软件解码器 → **我们就是分发方**。如果改成"用户自备 mpv、我们只负责连上去"，
  分发方就不是我们了 —— 这是很多开源项目实际采用的方式。
- **光改用 GPU 硬件解码不免责**：解码器代码仍然在我们分发的二进制里。
- **别只盯着 H.265**：H.264/AVC、AAC 同样在池子里。
- 风险是分级的：个人自用和小范围免费分发，实际被追责的概率很低（VLC、mpv、Kodi
  这些业内老牌都这么分发）；**收费、预装、面向企业分发是完全不同的量级** ——
  那才是真正会发生诉讼的地方。

三条现实路线，按"代价"排：**现在**不动代码，只把许可文本和说明补齐、把
`CODECS.md` 写准；**要公开发布安装包**时，考虑不分发 mpv（用户自备）或提供
"不含 HEVC"的构建；**要商业化**就必须买许可或砍掉软件解码、改走平台解码器。

## 二、没定的 / 要再想的

- **「像不像标题」那道筛子会误杀真标题（要不要放宽，得您定）。** 实测：
  BubbleUPnP 给视频的 `dc:title` 是 `Screenrecording_20260911_000943`，
  被 `looksLikeATitle` 判成"不像标题"跳过（罪名是"连续 5 位以上数字"，
  它命中了 `20260911`），最后界面显示类型名「视频」。
  **vivo 相册给的标题也长这样**（`Screenrecording_20260911_000943.mp4`，
  还带扩展名）—— 两家都一样，说明这不是个别现象。
  而**手机相机/截图的文件名几乎全是这个形状**（`IMG_20260911_123456`、
  `Screenshot_20260905_232916`、`VID_...`）—— 也就是说这道筛子在最常见的
  那类内容上会稳定失效。当初定它出来是为了挡 `1000140373` 这种内部编号，
  代价当时没量到。三个方向：把连续数字的阈值提高（比如 10 位以上才算编号）、
  只对"纯数字+分隔符"的串判成编号、或者干脆对**协议给的**标题放宽、
  只对"从 URL 推出来的"用严规矩。
- **自己画的云母底有几处取不到色，退回那块灰（#F3F3F3）：** 桌面背景是纯色、
  幻灯片、或者 Wallpaper Engine 那种第三方动态壁纸时，`SPI_GETDESKWALLPAPER`
  给的路径可能没有内容。另外壁纸铺法我们按"填充"算（Windows 默认也是它），
  桌面设成"平铺 / 居中 / 适应"时这份底和**真实桌面对不上** —— 但窗口里各块底
  之间仍然对得上（它们本来就是同一张图上裁下来的）。

  （原先这里还有一条"开关按 `availableEffects` 显示、所以 Win10 藏起来"——
  已经放开了：底色是我们自己算的，Win10 一样能用，藏起来只是把人挡在外面。
  同样的门槛在 `MicaBackdrop.micaOn` 和 `SettingsPage` 里都去掉了。）
- **加第二个协议之前必须先做的一步：把界面从 `DlnaRenderer` 上摘下来。**
  `TrayIcon` / `MainWindow` / `WindowsMediaControls` 现在都直接 include 了
  `protocols/dlna/DlnaRenderer.h`，手上只认识这一个门面。后果：新协议会有
  自己的门面，而界面只认第一个 —— **第二个协议投过来的东西，界面看不见、
  也控制不了**。

  要解开就得抽一层中性的"接收器"接口（谁连着 / 在放什么 / 命令往哪发 /
  勿扰开关），界面只认它，DLNA 和 AirPlay 各自去实现。**这和"把协议搬到
  后台线程"其实是同一件事的两面**：界面既不该知道协议在哪一层，也不该知道
  它跑在哪根线程上。

  （中立层本身是干净的：DIDL 的字段名、SOAP/GENA/SSDP 那些词、数值换算，
  全在 `protocols/dlna/` 里；`core/` 一个协议头文件都不 include。
  这次顺手把 `PlaybackController` 日志里写死的 "DLNA 投送" 也摘掉了 ——
  协议名现在由协议层自己填。）
- **歌词：读进来了，但还没有地方显示它。** 文件标签里的歌词会落到
  `NowPlaying.lyrics`（并暴露给 QML），日志里也会报一行"文件自带标签：…"。
  缺的是个界面（控制栏？独立面板？）和"歌词怎么排版"的定夺。
  另外**"歌词那个键到底叫什么"没验证成**：mpv 自带的编码器写不进自定义标签
  （ffmpeg 的封装器只认自己那张键表，`lyrics` 被丢掉了），所以造不出样本。
  要看准的话，投一首带内嵌歌词的歌，日志里那行"文件自带标签"会直接把它
  的名字和字数打出来。
- **陈旧订阅**：手机不是正常退订、而是直接走掉（关 Wi-Fi、没电）时，界面会
  一直显示"已连接" —— GENA 订阅有 30 分钟超时，我们不会主动去问它还在不在。
  日志里已经有一句"写完了，但对方一直没回话"，说明**我们知道对方没接**，
  只是没拿这个当成"它走了"。可以考虑加一条"连续几次推不动就当成断开"，
  那样手机走出范围时电脑这边能自己回到"未连接"。
- **网络协议要不要拆到后台线程**：**现在一个都没拆，协议全在主线程上** ——
  `SsdpService`（QUdpSocket）、`HttpServer`（QTcpServer）、`GenaManager` 都是
  Qt 的异步 socket 对象，靠事件循环收发，平时不占线程；代价是哪次解析或者
  处理卡一下，界面会跟着一起卡。将来协议多了（AirPlay / LeLink…）可以把整个
  协议层搬到一个带事件循环的 `QThread` 上 —— 它们都是 Qt 的 socket 对象，
  搬得动。**他说"到时候再说"，先记着。**

  > 顺带把线程现状记在这儿，省得下次再查一遍：整个进程里**只有 `MpvCore`
  > 的事件线程是我们自己开的**（`std::thread`，跑 `mpv_wait_event`，信号用
  > 队列连接送回主线程）；mpv 内部还有自己的线程；QML 的绘制在 Qt Quick 的
  > 渲染线程上（`MpvQmlItem` 的 render 就在那儿）。**托盘、旧界面、新界面
  > 三块都在主线程** —— 它们分别是 QSystemTrayIcon/QMenu、QWidget 和
  > QQuickWindow，Qt 要求它们必须待在主线程，挪走会崩。
- **关窗确认框的宽度写死 560。** 库自带的是 400，而它的高度是按"消息占一行"
  算的 —— 英文那句在 400 里折成两行之后**第二行会被切掉**，按钮上的
  "Close and disconnect" 也会被挤出框外。以后加语言如果哪一句更长，
  先看 `NewUiWindow.qml` 里那段注释。
- **顶栏样式**：现役是 `FluPivot`，观感偏 Windows 10。要 Win11 的样子得用
  我们自己写的 `TopNav.qml`（支持图标、支持左右分列）—— 它现在是**停用**
  状态，没进 `.qrc`，文件头和 `.qrc` 的注释里写了怎么启用。

### 界面上的几个时间常数

散在各文件里、但改的时候要一起想的四个数（各自文件里都有注释，这里汇总一眼）：

| 常数 | 值 | 在哪 | 为什么是这个数 |
|---|---|---|---|
| 淡入淡出 | **167 毫秒** | `MediaBar` 的 `opacity` Behavior | Fluent 这套库自己用的就是它（库里 39 处动画都是） |
| 静止画面收回 | **3 秒** | `MediaBar.idleTimer` | 他定的"停手、或者挪到界外，几秒后再收" |

### 别踩的坑

- **切全屏会让整个窗口渲染不出来（全黑），退出也回不来。** 症状是：切进全屏之后
  窗口铺满、样式也对、客户区几何也正常，但**里面什么都没画**（全黑），Esc 退出后
  还是黑的。

  **治法**：**切之前先 `visibility = Window.Hidden`，再 `showFullScreen()`**；退出
  那一步同理。等于把渲染面丢掉、让它重建一次。

  **为什么**：Windows 把窗口换成无边框（WS_POPUP）时，Qt 那层渲染面不跟着重建。
  排查时逐个排除过的（都还是黑）：把 mpv 的画面 item 藏起来、关掉云母（不着色器）、
  去掉启动时那次离屏预渲染；也量过客户区几何是全屏大小、样式位正常；
  而**一个最朴素的 Qt 窗口（同样的 OpenGL 后端）全屏是好的** —— 所以问题在
  "这个窗口 + 库的边框助手"这一层，不在 Qt 本身。见 `NewUiWindow.qml` 里
  `enterFullscreen` 那段注释。

- **退出全屏的两种还原方式不一样。** 位置和尺寸**不要自己存、自己摆**：写过一版，
  量下来是多余的（Qt 自己那份"进全屏之前的普通几何"很准：335,18 → 全屏 → 335,18），
  而且自己存还会踩坐标系的坑。但**最大化**那档要**直接 `showMaximized()`、不要先
  `showNormal()`** —— 先 normal 再 maximized 会落回普通窗口（实测）。

- **"点画面"的单击要等 250 毫秒再执行。** 因为双击画面 = 切全屏，而 Qt 对一次双击
  会先发一个 `clicked`、再发 `doubleClicked` —— 实测单击那一下会把播放/暂停**真的
  切一次**（不是"切两次净效果不变"，我一开始这么以为，日志打了脸）。所以单击先
  记着，来了双击就取消它。**控制栏中间那个键不受影响，仍然是立即的。**

- **量窗口位置/尺寸的探针脚本，坐标可能被 Windows 换算过。** 那几个 `.ps1` 里
  `SetProcessDPIAware()` 叫得晚一点，`SetWindowPos(400,60)` 实际会把窗口摆到
  (500,75)（125% 缩放）。有一轮我把这个当成"程序退出全屏后位置偏了 84 像素"，
  查了半天 —— 其实是**探针自己的问题**。要判断这种事，用**同一个工具**在切换前后
  各量一次（`grab-qml-window.ps1` 会打印 `picked window 宽x高 at x,y`）。

- **关窗 = 真的销毁窗口对象，所以那个裸指针必须跟着清。**
  FluentUI 的 `FluWindow` 默认 `autoDestroy: true` 就会销毁窗口，而
  `NewUiWindow` 拿的是裸指针 `m_window` —— 它不会自己变空，下一次投屏进来
  调 `m_window->show()` 就崩在 Qt6Gui 内部读非法地址（`Qt6Guid+0x34BA22`，
  连崩四次才查清）。**别把 `destroyed` 那条清理去掉。**
  关窗策略写在 `NewUiWindow.qml` 的 `closeListener` 里：有投送先弹框问，
  确认了才真关。
- **同一个进程里加载第二个 `QQmlApplicationEngine` 会崩**（实测崩在 Qt6Qml
  的 `m_engine->load()` 上）。所以规矩是：**引擎一个进程只建一次，窗口可以
  建了又销毁**。改 `NewUiWindow::load()` 之前先看那段注释。
- **QML 里切页不能藏起 `MpvQmlItem`。** render API 靠每帧渲染推着走，
  一藏起画面 item，mpv 的视频输出就停了 —— 再开也起不来（表现是"状态显示
  在播、位置一直是 0、画面全黑"）。设置页是**盖上去**的，不是换掉投屏页。
- **不要用 `checked: X.y` / `value: X.z` 这类绑定去接开关和滑块** ——
  控件一被用户操作，绑定当场就断了。统一用 `Component.onCompleted` 起手 +
  `Connections` 跟外部变化 + 点击时写回。
- **`FluWindow` 的 `appBar` 上，我们自己的按钮必须单独
  `window.setHitTestVisible(item)`**，否则按下去是拖窗口。窗口那三个按钮
  `FluWindow` 已经替我们登记过了，**两组必须分开**。
- **`FluWindow` 用了 `Component.onCompleted`**，实例上再写一个可能把它顶掉
  （窗口就不显示了）—— 改用 `AppTopBar` 的 `ready()` 信号。
- **图标名要核对** `third_party/FluentUI/src/FluentIconDef.h`（踩过：
  `TvMonitor` 实际是 `TVMonitor`）。
- **窗口"露面"到"画上第一帧"之间，那段时间窗口表面是透明的。** 用户看到的
  是：边框和阴影先出来，里面还是后面那些窗口，一秒多之后内容才刷上来
  （探针 `work/cap-flash.ps1`：窗口阴影出现之后，内部那个点还要 1.4 秒才变色）。
  **光声明 `Window.color` 没用** —— 那段时间根本没有渲染过任何一帧，清屏色
  没机会生效（试过，量的结果和改之前一模一样）。现在这么治：
  `autoVisible: false` + `visible: false`（**两个都要**：前者只管库自己那次
  show()，QML 的 Window 本身默认 `visible: true`）+ `NewUiWindow::show()` 里
  先 `grabWindow()` 离屏渲染一帧再 `show()`。改完透明那段降到约 0.1 秒，
  而且落在那扇窗自己的淡入动画里。代价：窗口出现晚约 2 秒（这份初始化开销
  从"露面之后"挪到了"露面之前"）。
  壁纸那张图也跟着改成**同步解码**（`asynchronous: false`）—— 否则会先看到
  一小会儿灰底再变成云母（量到约 0.3 秒，改完约 0.1 秒）。
- **Qt 6 的 QML 里，`Screen` 没有 `geometry` / `virtualX` / `virtualY`。**
  那是 Qt 5 的 API，Qt 6.11 的 `Screen`（`Window.screen` 和贴附属性都一样）
  只有 `width/height/desktopAvailableWidth/Height/devicePixelRatio/...`。
  写了一不会报错，只会拿到 `undefined`，然后**整块底变成一张空图** ——
  日志里那行 `Unable to assign [undefined] to QRectF` 是唯一的线索。
  库自己那份 `FluWindow` 的背景（`com_background`）里还在用
  `window.screen.virtualX`，所以在 Qt 6 下**它那条彩色的云母路径本来就是坏的**。
  我们这边：尺寸用贴附属性 `Screen.width/height`，屏幕原点用
  `FluTools.desktopAvailableGeometry(window)`（任务栏在右侧/下侧时它是准的，
  在左侧/上侧会差一个任务栏的厚度 —— 过一遍模糊就看不出来了）。
- **`ShaderEffectSource` 采不到 `visible: false` 的源。** 写 `visible: false` 的
  壁纸图，采到的是一张**空图**，模糊出来什么都没有（屏幕上只剩染色层盖在底色上，
  看着像一块发白的灰）。要么让源保持可见（我们让亚克力整个盖住它），
  要么用 `hideSource`。
- **祖先的 `clip` 会污染 `ShaderEffectSource` 的源渲染。** Qt 把源 item 渲染进
  纹理时连裁剪一起算，于是顶边那圈用来当"模糊邻域"的像素是空的 ——
  页面上的底和窗口那层因此对不齐，接缝上一条横线。**壁纸图必须放在不被裁的
  那一层**（我们放在窗口背景里，页面只借用它）。
- **QML 里别用 `mapToItem` 算位置，也别把位置算在"只在某个属性变化时才重算"
  的绑定里。** 实测 `mapToItem(win.contentItem, 0, 0)` 恒返回 `(0,0)`
  （把父级 x/y 一层层加起来得到的是正确的 48）；而且绑定只认**被读到的属性**，
  `mapToItem` 在 C++ 里读 item 自己的 x/y，引擎看不见 —— 锚点又是创建之后才落的，
  于是算一次就定死。`MicaBackdrop.originInWindow` 现在是自己沿 `parent` 累加。
- **脚本里的 exe 路径别写死构建目录名。** 清掉旧构建目录之后，那些
  `mcast-build2` / `mcast-build5` 之类的写死路径全烂了，症状是"程序起来了
  又立刻没"或者一串"目标计算机积极拒绝"。现在统一指向 `mcast-build11`。
- **别用 `monkey -c android.intent.category.LAUNCHER` 启动模拟器里的 App。**
  实测它把 MuMu 自己的"游戏中心"和"设置"给拉起来了（症状：`mCurrentFocus=null`，
  屏幕上是游戏中心）。原因是电视类应用（AirScreen 这种）的入口挂的是
  **LEANBACK_LAUNCHER** 而不是 LAUNCHER，monkey 匹配不到就开了别的。
  稳的写法是先问系统：`cmd package resolve-activity --brief <包名>` 拿到入口组件，
  再 `am start -n <组件>`。`mc-adb.ps1` 的 `Start-McApp` 已经改成这个顺序了。
- **别用固定坐标点模拟器里的界面。** 坐标会随着"上一个页面停在哪儿""设备列表里
  多了个设备"整体错位，而且点空了看不出来（表现为"什么都没发生"，很难查）。
  要么按文字找控件（`Find-McNode`），要么**人点、我们只负责量** —— 后者反而最快，
  配 `start-cap.ps1` / `stop-cap.ps1`（抓包丢在客机里跑，不受会话影响）。
- **同一台安卓里两个 App 之间的通话走 loopback**，抓 `wlan0` 是 0 个包，
  要抓 `lo`。
- **跑在模拟器里的接收器会被 Android 冻结**：切到后台后它对外还宣称老端口、
  实际已经不监听（现象是一串 RST）。MuMu 设置里的「应用保活」打开就稳了。
  另外这类接收器的 UPnP 端口**每次重启服务都会换**，别缓存。

> 顺带：那些脚本起了 MCast 之后**不会**自动挂 Qt 的 DLL 目录，不挂的话
> 进程会立刻退出。`mpvcore-regression.ps1` 里已经补了一行，别的脚本大多
> 本来就有。

### 模拟器测试台（真机控制点，可脚本驱动）

用一台 MuMu 里的 BubbleUPnP 当**真实控制点**：它比手机强的不是"更像真机"，
而是**可脚本驱动、可重复、能同时拿到截图 + UI 树 + logcat**。它只负责"按真实
控制点的按钮"；注入畸形请求那半边得靠我们自己写的测试控制点（别混）。

环境（2026-09-14 打通）：

```
D:\Apps\MuMuPlayer\nx_main\adb.exe     用 MuMu 自带的 adb（版本对不上会掉线）
实例名「娱乐（ROOT）」                  KernelSU 的 su 可用：uid=0, u:r:ksu:s0
adb：10.180.157.202:5555               桥接后的局域网地址
BubbleUPnP：com.bubblesoft.android.bubbleupnp
```

**桥接模式有两个坑**（都踩过）：

1. **切桥接之后 `127.0.0.1:16384` 那条端口转发就死了** —— 它绑在 NAT 那条老
   路径上。而 `MuMuManager.exe info -v all` 重启后照样一口咬定
   `"adb_port": 16384`，实际上那个端口没人监听。别信它，改连客机的
   `局域网地址:5555`。
2. **怎么找到客机的地址**：`vms\<实例名>\macaddress` 里是它的 MAC
   （`0839A0E78F73` 这种），展开成 `08-39-A0-E7-8F-73` 去宿主 `arp -a` 里对，
   翻出来的 `10.x.x.x` 就是它。（没现成 ARP 条目就先 ping 一下网段。）

顺带记：模拟器里 FlClash 的 VPN 是开着的（`tun0` 接管全流量），但它的绕过列表
含 `10.*`，所以到渲染器的流量是直连的。以后 SSDP 行为怪，先怀疑它。

**他不能双击构建目录里的 exe**（缺 Qt DLL），每次都得用 PATH 挂上 Qt 的 bin
才跑得起来 —— 一直是这边帮他跑的。
