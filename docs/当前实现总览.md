## 1. 当前产品形态

Media Cast Receiver 是 Windows 上的媒体投送接收器。当前实际支持
**DLNA / UPnP AV**，可接收视频、音频和图片；Google Cast、AirPlay、Miracast 尚未
实现。

主功能已经可用：

- 手机通过 DLNA 投送，电脑使用 libmpv + QML 播放；
- 视频、音频、图片、上一首/下一首、播放/暂停、进度、音量和画面调节；
- 原生托盘、启动屏幕、按需主窗口、全屏和 Windows 系统媒体控件；
- 语言包、深浅模式、Windows 强调色、Mica 回退、接收开关和广播设置；
- DLNA 投送确认窗口、同一 owner 换片、主动断开和 Stop 后空闲收口；
- 中性播放规划支持普通原生 URI、纯图片序列和“PNG 壳 + MPEG-TS”兼容路线。

用户界面里明确尚未完成的主功能是**字幕选择**。播放核心已经读取歌词数据，但
界面尚未展示。

## 2. 三进程

```text
MCast.Shell.exe        Win32，无 Qt
├─ 托盘、启动屏幕、单实例、持久配置、语言包扫描
├─ 启动并监督 MCast.Protocol.exe / MCast.Ui.exe
│
├─ MCast.Protocol.exe
│    无 Qt；SSDP / HTTP / SOAP / GENA / DLNA / Claim / 媒体规划
│
└─ MCast.Ui.exe
     Qt 6 / QML / FluentUI / libmpv / SMTC / 元数据过滤与展示
     只在至少一个 UI 窗口需要显示时存在
```

关键事实：

- Shell 常驻；Protocol 常驻；UI 按需启动。
- `--background` 只不启动 UI，不是“不启动网络”。
- Protocol 不直接启动 UI，只向 Shell 发 `UiActivateRequest`。
- UI 不解析 DIDL；协议专属对象不能穿过 PlaybackPipe。
- ControlPipe 负责身份、设置、确认和 UI 激活；PlaybackPipe 负责播放命令、快照和
  遥测。

## 3. 媒体与协议链路

```text
DLNA 控制点
  -> Protocol 解析并形成中性媒体记录
  -> Claim / owner 权限检查
  -> DlnaSession 保存当前、下一条和历史
  -> PlaybackPipe 下发中性播放命令
  -> UI 统一过滤元数据、执行 MPV/图片序列/剥壳代理
  -> QML 与 SMTC 消费同一个 NowPlaying
```

 Protocol 是网络会话、媒体队列和逻辑 transport 状态的权威；UI 是实际播放测量、
音量、位置、缓冲和渲染的权威。Protocol 只缓存 UI 上报事实来回答 SOAP/GENA。

## 4. 当前投送策略

- 任意时刻最多一个 owner。
- 生产 DLNA Runtime 当前使用“允许抢占、抢占前确认”：确认超时 10 秒，旧会话
  退场记录超时 5 秒，最多保留 8 条退场记录。
- 同一 owner 更换媒体不弹确认；不同控制点抢占才进入确认。
- 确认前旧投送继续；拒绝、关闭、超时和 UI 不可用都 fail-closed。
- 抢占、是否隐藏发现等策略目前尚未进入 `MediaCast.json` 和设置页。

确认窗口本身已经有独立 QML 模式 `--confirmation-only`，但 Shell 的普通冷启动链
还没有按需选择该模式。当前没有现成 UI 连接时，确认请求会安全拒绝。

## 5. 故障恢复现状

| 故障 | 当前结果 |
|---|---|
| UI 崩溃或首帧超时 | Shell 清理 UI 和启动屏幕；下一次激活可重新启动 UI |
| Protocol ControlPipe 断开 | Shell 清除协议连接，但**不会自动重启 Protocol** |
| Shell 崩溃 | Job 关闭，Protocol/UI 一起结束；没有反向拉起 Shell |
| 仅 PlaybackPipe 断开 | Protocol 重建 listener，经 Shell 通知现有 UI 重连；窗口和 MPV 不重建 |
| DLNA 网络面失败 | Runtime 可独立重建 HTTP/SSDP/GENA；不等于进程重启 |

`RestartController` 目前只有纯策略和单元测试，没有接入生产 Shell。进程自动重启和
反向监督仍属于待办。

## 6. 构建与验证

规范验证目录是仓库相对的 `out/build/x64-Debug`，默认 libmpv 开发包位于
`../../runtime/mpv-dev`。当前 CMake 配置注册 **40 项 CTest**。

2026-11-12 本轮较大改动曾完成 clean build 和 40/40 全量通过；本次文档归档只执行
了只读的 `ctest -N`，没有重新运行全套测试。今后引用通过率必须同时写明日期和
构建目录，不能用“当前 40 项”代替“刚才全通过”。

目前没有 `install()`、CPack 或一键 `windeployqt` 发布流程。

## 7. 最危险的硬约束

1. 改过头文件或 CMake 结构后使用 clean-first，避免 struct layout 不一致造成
   “链接成功、运行即崩”。
2. 确认、拒绝、超时和 UI 不可用只能 fail-closed，不能让候选在未确认时取得
   owner。
3. DLNA Claim 必须同时守住 `sessionId + epoch + mediaGeneration +
   operationId/requestId`，迟到命令不能穿透新媒体边界。
4. 高频媒体命令必须有界、可合并；Open/Stop/Next/Previous 等顺序边界不能被吞。
5. QML、窗口和渲染只在 UI 主线程操作；Protocol 和 Shell 不创建 Qt 窗口。
