## BubbleUPnP

版本/环境：MuMu 模拟器（桥接，`10.180.157.202`），2026-09-14 01:28～01:31。
渲染器：Media Cast Receiver（`10.180.157.193:8200`）。

### 选中一台渲染器之后，它按这个顺序来

```
1:30:48.441  SUBSCRIBE /RenderingControl/event
             回调地址 http://10.180.157.202:58645/dev/<设备 UID>/svc/upnp-org/RenderingControl/event/cb
1:30:48.445  GetTransportInfo
1:30:48.449  GetPositionInfo
1:30:48.469  Stop
1:30:48.548  我们推了一条 RenderingControl 事件（SEQ=0）→ 它回 200 OK
1:30:50.488  GetTransportInfo
1:30:52.491  GetTransportInfo      ← 之后每 2.000 秒一次
1:30:54.494  GetTransportInfo
1:30:56.497  GetTransportInfo
```

**两件值得记的事**：

- **它会发 Stop，哪怕什么都没装。** 当时旧实现回了
  `701（Transition not available）`，它看起来不受影响。现行 Claim 层为保护可能
  存在的旧 owner，对**未知来源**的 Stop 返回成功但忽略；只有已建立 owner 且确实
  无媒体时才由 SoapRouter 返回 701。这个差异不能再用旧抓包解释当前行为。
- **轮询节奏是 2 秒，而且只轮 GetTransportInfo**（这一段里没再轮
  GetPositionInfo）。进度条的原始数据大概另有来路（拖进度、播放中另说），
  要接着量。

### 发现阶段（SSDP）

- 一次搜**四样**，挨着发：
  `AVTransport`、`ContentDirectory`、`av-openhome-org:service:Product:1`、
  `urn:bubblesoftapps-com:service:Main:1`（最后这个是它在找自家的
  BubbleUPnP Server）。
- 对 `AVTransport` 的 M-SEARCH 写着 `MX=3`，但实际是**每 500 毫秒重发一次、
  连发三轮**，并没有等满 3 秒。三次我们都回了，它也都收下了。
- **它在找 OpenHome。** 这条值得单独留意：OpenHome 才是"播放列表/队列能连贯"
  的那套协议（UPnP AVTransport 的 SetAVTransportURI 只是"换一条放"，
  控制点得自己维护队列，所以 vivo 和 BubbleUPnP 的上一首/下一首才会各说各话）。
  我们没提供 OpenHome —— 将来真要做队列，这是唯一靠谱的方向。

### 订阅

- 回调地址里嵌的是**我们的设备 UID**（`/dev/<uid>/...`），说明它拿 UID 当设备身份。
- 第一次推送它回 `HTTP/1.1 200 OK`，正常。
- **它只订阅 `RenderingControl`，从头到尾没订阅过 `AVTransport`。**
  量了 40 分钟，跨越"选中设备 / 播放它自己的文件 / 反复切界面"三种情形，
  一次 AVTransport 的 SUBSCRIBE 都没有。（对比：vivo 相册那台是两个都订。）
- **而且它会退订再重订**：`01:41:19 UNSUBSCRIBE` → `01:41:36 SUBSCRIBE`，
  中间隔 17 秒。看着像"界面离开再回来"就重订一次。
- 推论（还没验证）：它把 AVTransport 那一侧**完全交给轮询**，
  事件只用来盯音量。所以"控制点为什么会显示错"这类问题，对它来说不是
  我们推得对不对，而是**我们回答得对不对**。

### 播放一条它自己的内容：完整控制序列

场景：用它**自己的媒体库**（文件在客机 `/sdcard/Movies`）投给我们，
2026-09-14 01:42:08。数据来自两边对账 —— 客机里 `tcpdump` 抓的包 + 我们的日志。

```
01:42:08.735  Stop                       ← 连着两条，它习惯先把设备按停
01:42:08.779  Stop
01:42:08.827  SetAVTransportURI   （1648 字节，带 DIDL）
01:42:08.839  SetPlayMode
01:42:08.849  GetTransportInfo
01:42:08.858  GetPositionInfo
01:42:08.963  Play
01:42:10.898  GetTransportInfo
01:42:10.931  GetPositionInfo
01:42:10.964  GetPositionInfo            ← 33 毫秒后又来一条
01:42:11.997  GetPositionInfo
01:42:12.964  GetTransportInfo + GetPositionInfo
01:42:13.032  GetPositionInfo
01:42:14.064  GetPositionInfo
01:42:14.997  GetTransportInfo + GetPositionInfo
01:42:15.099  GetPositionInfo
01:42:17.030  GetTransportInfo           ← 之后回到 2 秒一次的心跳
```

两个节奏，记准了：

- **心跳：`GetTransportInfo`，2.000 秒一次**，雷打不动（整轮 36 次，中位 2.01 秒、
  最大才 2.048）。
- **刚开播那 7 秒：`GetPositionInfo` 密集起来**（约每秒一次，连 8 次），
  之后就不再问了。所以**播放途中进度条的中间值，它是自己拿时钟推的**，
  不是每次问来的 —— 这就是为什么一旦我们这边的状态没及时被它问到，
  它的条会继续动。

### 它发的 DIDL（原样，一次 1648 字节）

```xml
<DIDL-Lite xmlns="urn:schemas-upnp-org:metadata-1-0/DIDL-Lite/"
           xmlns:upnp="urn:schemas-upnp-org:metadata-1-0/upnp/"
           xmlns:dc="http://purl.org/dc/elements/1.1/"
           xmlns:dlna="urn:schemas-dlna-org:metadata-1-0/"
           xmlns:sec="http://www.sec.co.kr/"
           xmlns:pv="http://www.pv.com/pvns/">
  <item id="/external/video/media/-1730634595/1000000058"
        parentID="/external/video/media/-1730634595" restricted="1">
    <upnp:class>object.item.videoItem</upnp:class>
    <dc:title>Screenrecording_20260911_000943</dc:title>
    <dc:creator>&lt;unknown&gt;</dc:creator>
    <upnp:artist>&lt;unknown&gt;</upnp:artist>
    <upnp:albumArtURI>http://10.180.157.202:57645/extractart/video/&lt;一串哈希&gt;.jpg</upnp:albumArtURI>
    <res protocolInfo="http-get:*:video/mp4:DLNA.ORG_PN=AVC_MP4_BL_L3L_SD_AAC;DLNA.ORG_OP=01;DLNA.ORG_FLAGS=01700000000000000000000000000000"
         size="14419251" resolution="2276x1280" duration="0:00:27.000">
      http://10.180.157.202:57645/external/video/media/1000000058.mp4
    </res>
  </item>
</DIDL-Lite>
```

**最值钱的一行是那两个 `<unknown>`**：占位符是 **BubbleUPnP 自己填的**，
不是 vivo 的毛病。也就是说"副标题显示 unknown"这类现象在控制点圈里是普遍做法，
我们那道占位符筛子方向是对的，而且应该把它当成常态而不是特例。

（顺带确认：它 `dc:creator` / `upnp:artist` 都给视频填，我们的规矩是视频图片
不看艺术家、只看副标题 —— 这次正好印证了当初那个决定。）

### 它自己的样子（抓包里能看到的）

- `User-Agent: Android/15 UPnP/1.0 BubbleUPnP/4.6.6` —— 以后排查可以按它分版。
- 请求头写的是 `Soapaction`（不是全大写 `SOAPACTION`），还带 `Connection: Keep-Alive`。
  HTTP 头本来就不分大小写，但**有些渲染器是按字符串硬比的**，那类实现到这儿就翻车。
- **它同时还是个媒体服务器**：文件是它自己用 `http://<它自己的 IP>:<端口>/...`
  提供的，不是推流。所以它和渲染器之间是两条独立的路（控制 + 取流）。

## AirScreen（参照渲染器，Cling 实现）

版本/环境：MuMu 模拟器里的 Android TV 版 AirScreen
（`com.ionitech.airscreen`），2026-09-14 02:20～03:00，桥接地址
`10.180.157.202`。**它是"别人家的渲染器"**：拿它跟我们的实现对同一串请求的
回答，就是这份文档存在的意义。

它底层是 **Cling**（服务列表里能看到
`org.fourthline.cling.android.AndroidUpnpServiceImpl`）—— 那是 Java 圈里
照着 UPnP 规范写的那套库，当参照系很合适。

### 设备描述（`/upnp/dev/<uuid>/desc`）

```xml
<friendlyName>AS-SMA5560[DMR]</friendlyName>        ← 拿机型拼的，还伪装成 Samsung
<manufacturer>Samsung</manufacturer>
<modelName>AirScreen MediaRenderer</modelName>
<UDN>uuid:d186ed28-61d2-15c5-2def-bda62b5306f7</UDN>
<dlna:X_DLNADOC>DMR-1.50</dlna:X_DLNADOC>
<dlna:X_DLNACAP>av-upload,image-upload,audio-upload</dlna:X_DLNACAP>
<iconList>…一张 48×48 的 png…</iconList>
```

服务三件套和我们一样（AVTransport / RenderingControl / ConnectionManager），
但 URL 是 Cling 风格：没有扩展名，形如
`/upnp/dev/<uuid>/svc/upnp-org/AVTransport/{desc,action,event}`。
我们的是 `/AVTransport/{scpd,control,event}` + `/description.xml` —— 两条路都合规。

### 和我们逐项对照

| 项目 | AirScreen（Cling） | 我们 | 评 |
|---|---|---|---|
| `dlna:X_DLNADOC` | DMR-1.50 | DMR-1.50 | 一致 |
| `dlna:X_DLNACAP` | 有 | 没有 | 可选，不影响投送 |
| `iconList` | 有 | 没有 | 有些控制点会显示图标 |
| AVTransport 动作数 | 17 | 15 | 我方有意不声明录音动作 |
| RenderingControl / ConnectionManager | 11 / 3 个动作 | 12 / 3 | 动作集合按我方能力和兼容策略声明 |
| 事件变量 | AVT 1 个、RC 1 个、CM 3 个 | 同 | 一致 |
| **`Stop`（手上没内容）** | **HTTP 500 + Fault 501** | 未知来源成功但忽略；owner 无媒体时 701 | 见下 |
| **`Seek`（它不给拖）** | **HTTP 200 + 空 `SeekResponse`** | 我们真拖 | 见下 |
| RenderingControl 事件内容 | Mute / Loudness / **Volume** / VolumeDB / PresetNameList | **Volume** / Mute / Brightness / Contrast / Sharpness | 各自实现，都合规 |
| TCP 连接 | **keep-alive 复用**（整场只有两三条流） | 每条命令 `Connection: close` 新开一条 | 都能跑，它更省 |
| 控制端口 | **随机**（重启服务就换，46183 → 33835） | 固定 8200 | 它换端口会让缓存失效 |

**两条值得单独记住的**：

- **它给"没内容时的 Stop"回 501，还漏出 Java 异常**：

  ```
  HTTP 500  <faultcode>s:Client</faultcode>  errorCode 501
  errorDescription: Current state of service prevents invoking that action.
                    Attempt to read from field 'java.lang.String ca.c.c' on a null
                    object reference in method 'void ca.k.y(ca.c)'
  ```

  最后那句是**它自己泄漏出来的空指针信息**。规范上这种情况该回 **701
  （Transition not available）**，我们做的是规范那一条。而 BubbleUPnP 对 501
  和 701 一视同仁，都当"这台设备现在不让我 Stop"，接着照样干活。

- **它的 `Seek` 嘴上说成功**：`<u:SeekResponse/>`，HTTP 200，但实际不拖
  （要看广告才给拖）。**那个广告墙在协议层完全看不见** —— 控制点只会以为拖好了，
  然后继续按自己的时钟画进度条。这正好解释了我们之前遇到的"两边进度不一致"里
  属于控制点那一半。

### 顺带确认的两件事（控制点侧，与渲染器无关）

- BubbleUPnP 对 AirScreen 的行为，和对我们**一模一样**：只订阅
  `RenderingControl`（订完 AirScreen 立刻推一条初始事件）、每 2 秒轮一次
  `GetTransportInfo`。**说明"不订 AVTransport、靠轮询"是 BubbleUPnP 的做派，
  不是渲染器的锅。**
- AirScreen 推的初始 RenderingControl 事件是一份完整快照
  （`Mute/Loudness/Volume/VolumeDB/PresetNameList`，命名空间
  `urn:schemas-upnp-org:metadata-1-0/RCS/`）。我们推的是
  `Volume/Mute/Brightness/Contrast/Sharpness`，同一套外壳、同样带 `channel="Master"`。
- 200 秒里 BubbleUPnP 发了 **120 个 M-SEARCH** —— 它是真能刷。

### 测试台这边的经验（跟协议无关，但别忘）

- **AirScreen 的服务在后台会被 Android 冻住**：切片之后它对外还宣称老端口，
  实际已经不监听（现象是一堆 RST）。MuMu 设置里打开 **「应用保活」** 之后就稳了。
- 它的 UPnP 端口**每次重启服务都会换**，别缓存。
- 同一台设备里两个 App 通话走 **loopback**，抓包要抓 `lo`，抓 `wlan0` 是空的。

## vivo 相册（控制点，真机）

环境：真机，`10.180.157.166`，2026-09-14 凌晨，对着模拟器里的 AirScreen 投。
抓包在模拟器里做（`-i any`），手机收发的全部流量都录下来了。

### 它长什么样

```
User-Agent: Android/16 UPnP/1.0 Cling/2.0
```

**它自己也是 Cling 写的** —— 跟 AirScreen 同一套库。这条有意思：国内这个圈子里
Cling 的存在感比想象中大得多。

``` 
SUBSCRIBE .../RenderingControl/event    Timeout: Second-1800
SUBSCRIBE .../AVTransport/event         Timeout: Second-1800
Callback: <http://10.180.157.166:38381/upnp/dev/<渲染器UDN>/svc/upnp-org/.../event/cb>
```

- **两个服务都订**（BubbleUPnP 只订 RenderingControl）—— 所以"推事件有没有用"
  这件事，对 vivo 有用、对 BubbleUPnP 没用，**同一套实现要同时伺候两种人**。
- 1800 秒超时，观测窗口内没有续订。
- 回调地址里嵌的是**渲染器的 UDN**（Cling 的习惯）。

### 它怎么问

- **`GetPositionInfo` 大约每 1.0 秒一次**（BubbleUPnP 是每 2 秒问
  `GetTransportInfo`）—— 两种完全不同的风格：一个盯位置，一个盯状态。
- 换片/重投时习惯发三连：`Stop` → `SetAVTransportURI` → `Play`。
- 它给的 DIDL：`dc:title` **带扩展名**（`Screenrecording_20260911_000943.mp4`），
  `resolution="720×1600"` 用的是**乘号 `×`**（U+00D7）而不是 ASCII 的 `x`。
  规范示例里是 ASCII —— **谁要是拿它当数值解析就会踩坑**。

### 两个老毛病的判决（这是我们一直想知道的）

您描述过：在电脑侧暂停之后，手机显示"已暂停"但**进度条继续往前走**；在电脑侧
拖进度条，手机跳过去又**弹回旧位置**。这一次拿 AirScreen 当对照渲染器复现了
同样的现象 —— 而 AirScreen 是成熟的商业实现。**所以不是我们的锅。** 具体到数据：

**① 暂停后进度条继续走 —— 是 vivo 自己的 UI。**

暂停期间 AirScreen 报的位置是**冻住的**：

```
74.1  RelTime=00:00:39      ← 暂停中
75.1  RelTime=00:00:39
76.1  RelTime=00:00:39
77.2  RelTime=00:00:39
```

而 vivo 那 1 秒一次的轮询**一直在收这些值**（74.1 / 75.1 / 76.1 / 77.2 都问到了）。
它手里明明有"位置不动"的数据，进度条还是自己往前走 —— 只能解释成它的界面在
拿本地时钟插值，而不是用轮询回来的值。**渲染器这边修不了，也不该背这个锅。**

**② 拖进度回弹 —— 机制清楚了，责任在"插值 + 1 秒轮询"的组合。**

手机的进度条是"自己插值 + 每秒一次校正"驱动的。seek 之后如果渲染器还没落位、
报回旧值，下一秒的轮询就会把条**打回去**。AirScreen 的位置值本身跳动就很大
（实测能看到 `46→20`、`21→11` 这种倒退），所以这类控制点上回弹更容易出现。

### AirScreen 推回来的事件（规范实现的样本）

这是 BubbleUPnP 那条路永远看不到的东西，因为**它从不订阅 AVTransport**。

- **订阅时先推一份完整快照**：22 个字段，含 `AVTransportURI`、
  `AVTransportURIMetaData`（整份 DIDL）、`CurrentTransportActions`、
  `TransportState`、`NumberOfTracks`、`TransportPlaySpeed`……
- **之后只推变化的那几个**：

  ```xml
  <Event xmlns="urn:schemas-upnp-org:metadata-1-0/AVT/">
    <InstanceID val="0">
      <TransportState val="PLAYING"/>
      <CurrentTransportActions val="Stop,Pause,Seek"/>
      <CurrentTrackDuration val="00:00:53"/>
      <CurrentMediaDuration val="00:00:53"/>
    </InstanceID>
  </Event>
  ```

- 推送**很及时**：命令之后 0.3～0.6 秒就出去了。
- **事件里没有位置**（没有 `RelativeTimePosition`）。位置只走轮询 —— 和我们
  "事件报状态、轮询报位置"的分工一致。
- `CurrentTransportActions` 会跟着状态变：停止时是 `Play`，播放时是
  `Stop,Pause,Seek`，暂停时还多一个 `Play`。**这正是控制点决定按钮灰不灰的依据**，
  我们当初把它加回去是对的。

## 抖音（DMR 视频投送，真机，2026-11-12）

### 连续视频的投送方式

抖音滑到下一个视频时，不是在同一 HLS 里换镜头，而是重新发送一条独立的
`SetAVTransportURI`，每个视频都有自己的 `douyinvod.com` MP4 URL。正常切换顺序是：

```text
当前视频自然结束 -> STOPPED
SetAVTransportURI + Play
-> PREPARING
-> PLAYING
```

实测多次切换的起播间隔多为 0.1～0.8 秒，标题、URL 和 Windows 媒体控制会一起更新，
实际观感基本无缝。个别情况下抖音会把**同一个 URL 连续投两次**；当前 DLNA Claim
层会对同一 owner、相同 URI 和相同中性媒体字段的重复 SetURI 做幂等去重，只返回
成功，不再第二次 Open。

### MP4 里的 `vid:` 标签

抖音 MP4 自带：

```text
comment=vid:v2700fgi0000db8fqvfog65qrt5opl90
```

这个值不是 DIDL 的 `upnp:subtitle`，而是抖音写进文件元数据的内部视频 ID。
当前视频副标题的回退链会读取 MP4 的 `description/comment/synopsis`，所以控制栏和
Windows 媒体面板会显示成：

```text
副标题：vid:v2700fgi0000db8fqvfog65qrt5opl90
```

这是当前过滤管线的回退结果，不是 MPV 或渲染器凭空生成的内容。

候选过滤规则（先记录，暂不启用，等各控制点统一采样后再收口）：

```text
^vid:[A-Za-z0-9]+$
```

该规则应只作用于**副标题候选值**；不作为标题的唯一判据，也要避免误伤正常描述中
刚好包含 `vid:` 的文本。

## 哔哩哔哩官方（DMR 视频投送，真机，2026-11-12）

### 播放与切换

官方 App 投送视频时使用独立的 `bilivideo.com` MP4 URL；首条播放和手机端切换下一条
均正常。切换仍是新一轮 `Stop -> SetAVTransportURI -> Play`，不是同一媒体内切集。

### 副标题里的长随机串

视频开始加载前，Windows 媒体控制卡片的副标题就已经被填成一串约 400 字符的
URL-safe Base64 风格文本，例如：

```text
daZDGgtxp7XZlmtm8qvlnzyWXGVgObB-tUXXD7H8O_QCiPY1gRmh...
```

MP4 随后报出的文件标签并不包含这串文本：

```text
description=Bilibili VXCode Swarm Transcoder v1.3.46
encoder=Lavf61.7.106
```

因此这串“乱码”确定来自 B 站官方 App 的 DIDL 协议元数据，不是 MPV、文件名或
MP4 标签回退。它在 `protocol.subtitle / protocol.description /
protocol.long_description` 三者中的具体位置暂未单独打印；当前副标题回退链会让
它先于 `file.subtitle` 命中，所以后面的 `Bilibili VXCode Swarm Transcoder...`
也不会显示。

候选过滤规则（先记录，暂不启用）：

```text
^[A-Za-z0-9_-]{200,}$
^Bilibili VXCode Swarm Transcoder(?:\s+v[\d.]+)?$
```

第一条用于超长、无空格、整串都是 URL-safe Base64 字符的副标题候选；第二条用于
B 站转码器的技术描述。两条都只应作用于“视频/图片副标题候选”，不能用于标题。

## 腾讯视频「本地模式」（DMR 视频投送，真机，2026-11-12）

主界面的连接信息显示：

```text
控制点：未知
控制方式：未订阅远程控制事件
```

但“未订阅远程控制事件”不等于它不使用标准控制命令。腾讯仍会发送
`AVTransport#Pause`、`Play`、`Seek`，音量则通过
`RenderingControl#SetVolume` 调节；它只是不注册 GENA 控制点，也没有稳定的控制点名称。

### 身份分裂问题

腾讯把“投送”和后续遥控拆成了两组 HTTP 请求。投送媒体时使用的对端身份，与之后
暂停、seek、播放使用的身份不完全一致；后者经常没有可识别的 User-Agent。旧逻辑要求
完整身份匹配才允许控制，于是：

- 音量正常，因为 RenderingControl 不经过该控制授权检查；
- 暂停/seek 在 AVTransport 控制授权处被拒绝，控制点随后查询到仍在播放并回弹；
- 播放状态和媒体本身均正常。

兼容规则调整为：

```text
新投送 / 抢占媒体：仍要求完整 peer identity 匹配
当前会话的 Pause / Play / Stop / Seek：允许同一来源 IP 控制
```

这条规则在 2026-11-12 实测通过。它把“同一个 App 的控制请求换了身份”和“同 IP
另一个 App 尝试抢投送”区分开：前者允许，后者仍会进入正常的抢占确认流程。

本地模式的媒体 URL 形如手机临时代理：

```text
http://192.168.10.3:10991/proxy/.../vod.m3u8
```

播放器不需要针对腾讯做特殊解析；兼容点只在 DLNA 会话控制授权。

## 咪咕视频（DMR 视频投送，真机，2026-11-12）

官方 App 投送的是直接 HLS：

```text
http://hlsztemgspvod.miguvideo.com:8080/.../...mp4.m3u8?...&dlna=1
```

User-Agent 为：

```text
UPnP/1.0 DLNADOC/1.50 MGDLAN4Android/3.1.6
```

首投和普通播放能工作，标题、类型、画面和 Windows 媒体控制均正常，但控制行为
非常不稳定：

- 同一集短时间内重复发送 `SetAVTransportURI`，多次重载相同 URL；
- `Play` 会重复发送，并和 `GetPositionInfo/GetTransportInfo` 并发；
- 少量请求是空或损坏的 SOAP；
- 拖动进度条后连续发送多个目标相差很大的 Seek。实测包括 `0s`、`752s`、
  `1371s`，其中多个在 5 秒内没有得到完成结果而超时；
- 电脑端暂停几秒后，控制点会再次发送 `SetAVTransportURI/Play` 把播放拉回去；
- 拖动后控制点继续按自己的进度插值和投送，导致 UI 与手机进度长期不一致。

证据表明，主要问题是咪咕把“重载媒体、重新 Play、轮询、Seek”混在一起高频发送，
而不是接收器缺少某个专门的咪咕兼容规则。**不针对咪咕的遥控器和拖条逻辑制作特例。**

不过这轮实测暴露了两个属于接收器的通用可靠性问题：

1. **控制面被媒体面拖死。** 高频媒体命令期间出现
   `Playback IPC 写入失败：pipe I/O timed out`；随后用户点击电脑端“断开投送”时，
   对 PlaybackPipe 的断开请求连续失败。断开命令必须和媒体命令分路，至少不能被
   正在排队的 Open/Seek 阻塞。
2. **超时后所有权状态可能失稳。** `DLNA play callback failed` 和多次
   `playback command timed out` 之后，同一个
   `192.168.10.3|MGDLAN4Android/3.1.6` 发出的 Seek 被当成非 owner 拒绝。
   callback 超时应清理该命令，但不能把仍在活动的会话所有权一并弄丢。

这两项按“通用命令拥塞与状态一致性”修复，不做咪咕专属判断。

小红书只订阅：

```text
/AVTransport/event
```

没有订阅 `/RenderingControl/event`。日志中它只在建立投送时调用一次

读到电脑当前的真实音量。

遥控器与新视频起播状态经真机复测均正常，不列为同步问题。

## 通用观察：电脑端主动断开后，手机仍显示已连接

**观察时间：2026-11-12。** 在电脑端点击「断开投屏」后，接收器自己的状态会正确
切换到断开、无媒体，托盘和主窗口也不再显示当前投送；但手机端仍停留在“正在投屏”
或“已连接电视”的界面，表现为它不认为自己已经断开。

### 芒果 TV 实抓结果（2026-11-12 20:58:53）

抓包文件：`work/active-disconnect-20261112.pcapng`。手机为
`192.168.10.3`，接收器为 `192.168.10.4:8200`。

实际时间线：

```text
20:58:53.952  接收器向 239.255.255.250:1900 发出 6 个 ssdp:byebye
              分别覆盖 rootdevice、UDN、MediaRenderer、AVTransport、
              RenderingControl、ConnectionManager
20:58:53.955  Protocol 确认结束会话，HTTP/GENA/SSDP 下线
20:58:54.266  手机 SYN 到 8200，收到 RST
20:58:54.334  手机再次 SYN 到 8200，再次收到 RST
20:58:55.587  接收器重新开始 SSDP alive，HTTP 8200 恢复
20:58:55.910  手机重新连接并请求 GetPositionInfo
20:58:55.911  接收器回复 200，TrackURI 为空、时长为 0
20:58:56.851  手机轮询 GetTransportInfo
20:58:56.852  接收器回复 NO_MEDIA_PRESENT / OK
之后手机仍保持遥控器界面，并继续每秒轮询
```

本次抓包没有看到芒果 TV 的 `SUBSCRIBE` 或 `NOTIFY`，说明这一轮它没有订阅
GENA，只靠 SSDP 发现 + AVTransport 轮询。因此“最终 GENA 状态”对它没有作用。

结论：

- 接收器的 SSDP `byebye` 确实到了网线，报文类型、UDN、NTS 正确；
- 8200 确实停止过，手机也实际遇到 TCP RST；
- 服务恢复后，手机能读到 `NO_MEDIA_PRESENT` 和空 TrackURI；
- 芒果 TV 仍不主动退出遥控器界面，是控制点没有把 byebye、短暂断连或
  `NO_MEDIA_PRESENT` 当成“投送结束”。DMR 是服务端，没有反向命令控制点
  退出界面的标准动作。

### 主动断开的新顺序（2026-11-12 实现）

上一版先停网络面，再由 `EndSession` 异步收尾。现在改为：

```text
停止接受新的 SetAVTransportURI
  -> EndSession
  -> 等播放状态进入 NO_MEDIA_PRESENT
  -> 有限等待最终 GENA 队列排空
  -> 以短间隔重复 3 轮 SSDP byebye
  -> 停止 GENA / HTTP / SSDP
  -> 延迟 1.5 秒重新 alive，恢复接收
```

最终 GENA 排空最多等待 1 秒，避免某个失联订阅者无限拖住断开。GENA 订阅续订
本身不再续 Stop 空闲计时；只有当前控制点的实际 SOAP 活动或新的
`SetAVTransportURI` 才会取消等待。
整个主动断开另有 8 秒总 deadline。即使 EndSession 被上游拥塞或最终没产生
`NO_MEDIA_PRESENT`，也会强制停网络、延迟 alive，不会永久停在“正在断开”。
Claim 层现在只在授权判断和事务登记期间持有串行锁；真正可能等待 5 秒的 SOAP
Play/Pause/Stop/Seek 会在调用 Router 前释放该锁。因此新到的
`SetAVTransportURI` 不需要绕过校验抢跑，也不会被前一条同步控制命令堵到 8 秒
边界之后；它仍在正常 Claim 成功后调用 `newMediaRequested()` 取消 Stop 计时。

当前实现并不是先推 `STOPPED` 再清媒体。主动断开直接执行 `EndSession`，播放状态
进入 `NO_MEDIA_PRESENT`；随后等待最终 GENA 排空、发送三轮 SSDP byebye，再关闭
HTTP/GENA/SSDP。手机仍不退出界面的原因只能从控制点是否消费
`NO_MEDIA_PRESENT`、byebye、断连和后续查询来解释。

已知 DMR 是服务端，不能反向命令控制点退出界面；有些控制点可能只会在下一次查询或
用户操作时才发现设备已消失。因此后续应分别记录：

- 手机最终是立即退出、数秒后退出，还是必须手动退出；
- 该控制点是否订阅 AVTransport；
- 断开时收到的最后一条 GENA NOTIFY；
- 是否抓到了 SSDP `byebye`。

在明确控制点行为之前，不应把它和接收器内部的 `peerConnected` 状态混为一谈。

## 反向观察：手机主动退出投屏

同一轮真实日志里，芒果 TV 播放到 20:17:59 时发出了一条标准
`AVTransport#Stop`。接收器随后把播放状态正确切到 `STOPPED`，但手机没有再发送
任何控制请求、GENA 退订或额外断开指令；Protocol 的 `peerConnected` 仍保持为真。

这说明问题不在“手机完全没有通知”，而在接收器把 **Stop 只当成停止播放**，没有
把它当作控制点可能离开的前兆。DLNA 的 DMR 没有一个所有控制点都会发送的可靠
“客户端主动断开”动作，`Stop` 往往就是事实上的退出信号；但正常换片也会发
`Stop -> SetAVTransportURI`，所以不能在 Stop 时立即清空。

当前处理：

```text
Stop 成功
  -> 保留 8 秒 stop-idle grace
  -> 只有当前控制点同地址的后续 SOAP 活动会取消等待
  -> 其他设备查询、GENA 订阅/续订都不会续命
  -> 8 秒边界额外保留 250 ms，让恰好到达的 SetAVTransportURI 优先
  -> SetAVTransportURI 正常开始下一次投送
  -> 8 秒内完全没有后续活动：结束会话、清空播放列表并回到未投送
```

日志会分别记录等待开始和因 Stop 后持续空闲而结束会话，便于用真实 App 回归。
