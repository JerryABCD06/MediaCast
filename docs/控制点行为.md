# 控制点行为观察

> 这份记**真实控制点实际怎么做**，不记规范怎么写（规范那侧在 `DLNA实现情况.md`）。
> 每条都写清楚是在哪台设备上、什么时候量的。量法见 `待办.md` 的
> 「模拟器测试台」—— 一台桥接进局域网的 MuMu + 里面的 BubbleUPnP，
> 全程可以脚本驱动、截图、抓 logcat。
>
> 为什么值得单开一份：规范是"应该"，这里是"实际"。过去那些互操作坑，全是
> 两边的差距造成的，而差距只能靠观察攒。

## BubbleUPnP

版本/环境：MuMu 模拟器（桥接，`10.180.157.202`），2026-09-14 01:28～01:31。
渲染器：Media Cast Receiver（`10.180.157.193:8200`）。

### 选中一台渲染器之后，它按这个顺序来

```
1:30:48.441  SUBSCRIBE /RenderingControl/event
             回调地址 http://10.180.157.202:58645/dev/<设备 UID>/svc/upnp-org/RenderingControl/event/cb
1:30:48.445  GetTransportInfo
1:30:48.449  GetPositionInfo
1:30:48.469  Stop
1:30:48.548  我们推了一条 RenderingControl 事件（SEQ=0）→ 它回 200 OK
1:30:50.488  GetTransportInfo
1:30:52.491  GetTransportInfo      ← 之后每 2.000 秒一次
1:30:54.494  GetTransportInfo
1:30:56.497  GetTransportInfo
```

**两件值得记的事**：

- **它会发 Stop，哪怕什么都没装。** 我们回了 `701（Transition not available）`，
  它看起来不受影响（照样订阅、照样轮询）。规范上 701 是对的 —— AVTransport:1
  在 `NO_MEDIA_PRESENT` 下 Stop 不成立。但市面很多渲染器这里直接回 200，
  所以有互操作风险。**先记着，别急着改**：要改也得先拿真机验证它是不是真的
  在意这个失败码。
- **轮询节奏是 2 秒，而且只轮 GetTransportInfo**（这一段里没再轮
  GetPositionInfo）。进度条的原始数据大概另有来路（拖进度、播放中另说），
  要接着量。

### 发现阶段（SSDP）

- 一次搜**四样**，挨着发：
  `AVTransport`、`ContentDirectory`、`av-openhome-org:service:Product:1`、
  `urn:bubblesoftapps-com:service:Main:1`（最后这个是它在找自家的
  BubbleUPnP Server）。
- 对 `AVTransport` 的 M-SEARCH 写着 `MX=3`，但实际是**每 500 毫秒重发一次、
  连发三轮**，并没有等满 3 秒。三次我们都回了，它也都收下了。
- **它在找 OpenHome。** 这条值得单独留意：OpenHome 才是"播放列表/队列能连贯"
  的那套协议（UPnP AVTransport 的 SetAVTransportURI 只是"换一条放"，
  控制点得自己维护队列，所以 vivo 和 BubbleUPnP 的上一首/下一首才会各说各话）。
  我们没提供 OpenHome —— 将来真要做队列，这是唯一靠谱的方向。

### 订阅

- 回调地址里嵌的是**我们的设备 UID**（`/dev/<uid>/...`），说明它拿 UID 当设备身份。
- 第一次推送它回 `HTTP/1.1 200 OK`，正常。
- **它只订阅 `RenderingControl`，从头到尾没订阅过 `AVTransport`。**
  量了 40 分钟，跨越"选中设备 / 播放它自己的文件 / 反复切界面"三种情形，
  一次 AVTransport 的 SUBSCRIBE 都没有。（对比：vivo 相册那台是两个都订。）
- **而且它会退订再重订**：`01:41:19 UNSUBSCRIBE` → `01:41:36 SUBSCRIBE`，
  中间隔 17 秒。看着像"界面离开再回来"就重订一次。
- 推论（还没验证）：它把 AVTransport 那一侧**完全交给轮询**，
  事件只用来盯音量。所以"控制点为什么会显示错"这类问题，对它来说不是
  我们推得对不对，而是**我们回答得对不对**。

### 播放一条它自己的内容：完整控制序列

场景：用它**自己的媒体库**（文件在客机 `/sdcard/Movies`）投给我们，
2026-09-14 01:42:08。数据来自两边对账 —— 客机里 `tcpdump` 抓的包 + 我们的日志。

```
01:42:08.735  Stop                       ← 连着两条，它习惯先把设备按停
01:42:08.779  Stop
01:42:08.827  SetAVTransportURI   （1648 字节，带 DIDL）
01:42:08.839  SetPlayMode
01:42:08.849  GetTransportInfo
01:42:08.858  GetPositionInfo
01:42:08.963  Play
01:42:10.898  GetTransportInfo
01:42:10.931  GetPositionInfo
01:42:10.964  GetPositionInfo            ← 33 毫秒后又来一条
01:42:11.997  GetPositionInfo
01:42:12.964  GetTransportInfo + GetPositionInfo
01:42:13.032  GetPositionInfo
01:42:14.064  GetPositionInfo
01:42:14.997  GetTransportInfo + GetPositionInfo
01:42:15.099  GetPositionInfo
01:42:17.030  GetTransportInfo           ← 之后回到 2 秒一次的心跳
```

两个节奏，记准了：

- **心跳：`GetTransportInfo`，2.000 秒一次**，雷打不动（整轮 36 次，中位 2.01 秒、
  最大才 2.048）。
- **刚开播那 7 秒：`GetPositionInfo` 密集起来**（约每秒一次，连 8 次），
  之后就不再问了。所以**播放途中进度条的中间值，它是自己拿时钟推的**，
  不是每次问来的 —— 这就是为什么一旦我们这边的状态没及时被它问到，
  它的条会继续动。

### 它发的 DIDL（原样，一次 1648 字节）

```xml
<DIDL-Lite xmlns="urn:schemas-upnp-org:metadata-1-0/DIDL-Lite/"
           xmlns:upnp="urn:schemas-upnp-org:metadata-1-0/upnp/"
           xmlns:dc="http://purl.org/dc/elements/1.1/"
           xmlns:dlna="urn:schemas-dlna-org:metadata-1-0/"
           xmlns:sec="http://www.sec.co.kr/"
           xmlns:pv="http://www.pv.com/pvns/">
  <item id="/external/video/media/-1730634595/1000000058"
        parentID="/external/video/media/-1730634595" restricted="1">
    <upnp:class>object.item.videoItem</upnp:class>
    <dc:title>Screenrecording_20260911_000943</dc:title>
    <dc:creator>&lt;unknown&gt;</dc:creator>
    <upnp:artist>&lt;unknown&gt;</upnp:artist>
    <upnp:albumArtURI>http://10.180.157.202:57645/extractart/video/&lt;一串哈希&gt;.jpg</upnp:albumArtURI>
    <res protocolInfo="http-get:*:video/mp4:DLNA.ORG_PN=AVC_MP4_BL_L3L_SD_AAC;DLNA.ORG_OP=01;DLNA.ORG_FLAGS=01700000000000000000000000000000"
         size="14419251" resolution="2276x1280" duration="0:00:27.000">
      http://10.180.157.202:57645/external/video/media/1000000058.mp4
    </res>
  </item>
</DIDL-Lite>
```

**最值钱的一行是那两个 `<unknown>`**：占位符是 **BubbleUPnP 自己填的**，
不是 vivo 的毛病。也就是说"副标题显示 unknown"这类现象在控制点圈里是普遍做法，
我们那道占位符筛子方向是对的，而且应该把它当成常态而不是特例。

（顺带确认：它 `dc:creator` / `upnp:artist` 都给视频填，我们的规矩是视频图片
不看艺术家、只看副标题 —— 这次正好印证了当初那个决定。）

### 它自己的样子（抓包里能看到的）

- `User-Agent: Android/15 UPnP/1.0 BubbleUPnP/4.6.6` —— 以后排查可以按它分版。
- 请求头写的是 `Soapaction`（不是全大写 `SOAPACTION`），还带 `Connection: Keep-Alive`。
  HTTP 头本来就不分大小写，但**有些渲染器是按字符串硬比的**，那类实现到这儿就翻车。
- **它同时还是个媒体服务器**：文件是它自己用 `http://<它自己的 IP>:<端口>/...`
  提供的，不是推流。所以它和渲染器之间是两条独立的路（控制 + 取流）。

## AirScreen（参照渲染器，Cling 实现）

版本/环境：MuMu 模拟器里的 Android TV 版 AirScreen
（`com.ionitech.airscreen`），2026-09-14 02:20～03:00，桥接地址
`10.180.157.202`。**它是"别人家的渲染器"**：拿它跟我们的实现对同一串请求的
回答，就是这份文档存在的意义。

它底层是 **Cling**（服务列表里能看到
`org.fourthline.cling.android.AndroidUpnpServiceImpl`）—— 那是 Java 圈里
照着 UPnP 规范写的那套库，当参照系很合适。

### 设备描述（`/upnp/dev/<uuid>/desc`）

```xml
<friendlyName>AS-SMA5560[DMR]</friendlyName>        ← 拿机型拼的，还伪装成 Samsung
<manufacturer>Samsung</manufacturer>
<modelName>AirScreen MediaRenderer</modelName>
<UDN>uuid:d186ed28-61d2-15c5-2def-bda62b5306f7</UDN>
<dlna:X_DLNADOC>DMR-1.50</dlna:X_DLNADOC>
<dlna:X_DLNACAP>av-upload,image-upload,audio-upload</dlna:X_DLNACAP>
<iconList>…一张 48×48 的 png…</iconList>
```

服务三件套和我们一样（AVTransport / RenderingControl / ConnectionManager），
但 URL 是 Cling 风格：没有扩展名，形如
`/upnp/dev/<uuid>/svc/upnp-org/AVTransport/{desc,action,event}`。
我们的是 `/AVTransport/{scpd,control,event}` + `/description.xml` —— 两条路都合规。

### 和我们逐项对照

| 项目 | AirScreen（Cling） | 我们 | 评 |
|---|---|---|---|
| `dlna:X_DLNADOC` | DMR-1.50 | DMR-1.50 | 一致 |
| `dlna:X_DLNACAP` | 有 | 没有 | 可选，不影响投送 |
| `iconList` | 有 | 没有 | 有些控制点会显示图标 |
| AVTransport 动作数 | 17 | 17（我们也有全套） | 一致 |
| RenderingControl / ConnectionManager | 11 / 3 个动作 | 11 / 3 | 一致 |
| 事件变量 | AVT 1 个、RC 1 个、CM 3 个 | 同 | 一致 |
| **`Stop`（手上没内容）** | **HTTP 500 + Fault 501** | **HTTP 500 + Fault 701** | 见下 |
| **`Seek`（它不给拖）** | **HTTP 200 + 空 `SeekResponse`** | 我们真拖 | 见下 |
| RenderingControl 事件内容 | Mute / Loudness / **Volume** / VolumeDB / PresetNameList | **Volume** / Mute / Brightness / Contrast / Sharpness | 各自实现，都合规 |
| TCP 连接 | **keep-alive 复用**（整场只有两三条流） | 每条命令 `Connection: close` 新开一条 | 都能跑，它更省 |
| 控制端口 | **随机**（重启服务就换，46183 → 33835） | 固定 8200 | 它换端口会让缓存失效 |

**两条值得单独记住的**：

- **它给"没内容时的 Stop"回 501，还漏出 Java 异常**：

  ```
  HTTP 500  <faultcode>s:Client</faultcode>  errorCode 501
  errorDescription: Current state of service prevents invoking that action.
                    Attempt to read from field 'java.lang.String ca.c.c' on a null
                    object reference in method 'void ca.k.y(ca.c)'
  ```

  最后那句是**它自己泄漏出来的空指针信息**。规范上这种情况该回 **701
  （Transition not available）**，我们做的是规范那一条。而 BubbleUPnP 对 501
  和 701 一视同仁，都当"这台设备现在不让我 Stop"，接着照样干活。

- **它的 `Seek` 嘴上说成功**：`<u:SeekResponse/>`，HTTP 200，但实际不拖
  （要看广告才给拖）。**那个广告墙在协议层完全看不见** —— 控制点只会以为拖好了，
  然后继续按自己的时钟画进度条。这正好解释了我们之前遇到的"两边进度不一致"里
  属于控制点那一半。

### 顺带确认的两件事（控制点侧，与渲染器无关）

- BubbleUPnP 对 AirScreen 的行为，和对我们**一模一样**：只订阅
  `RenderingControl`（订完 AirScreen 立刻推一条初始事件）、每 2 秒轮一次
  `GetTransportInfo`。**说明"不订 AVTransport、靠轮询"是 BubbleUPnP 的做派，
  不是渲染器的锅。**
- AirScreen 推的初始 RenderingControl 事件是一份完整快照
  （`Mute/Loudness/Volume/VolumeDB/PresetNameList`，命名空间
  `urn:schemas-upnp-org:metadata-1-0/RCS/`）。我们推的是
  `Volume/Mute/Brightness/Contrast/Sharpness`，同一套外壳、同样带 `channel="Master"`。
- 200 秒里 BubbleUPnP 发了 **120 个 M-SEARCH** —— 它是真能刷。

### 测试台这边的经验（跟协议无关，但别忘）

- **AirScreen 的服务在后台会被 Android 冻住**：切片之后它对外还宣称老端口，
  实际已经不监听（现象是一堆 RST）。MuMu 设置里打开 **「应用保活」** 之后就稳了。
- 它的 UPnP 端口**每次重启服务都会换**，别缓存。
- 同一台设备里两个 App 通话走 **loopback**，抓包要抓 `lo`，抓 `wlan0` 是空的。
