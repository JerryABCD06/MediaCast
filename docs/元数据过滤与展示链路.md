# 元数据过滤与展示链路

更新时间：2026-11-12

## 一、硬边界

```text
协议原始数据
  -> Protocol：解析成中立但未过滤的字段，并保存原始媒体记录
  -> Ui：统一过滤、回退，形成唯一的 NowPlaying
       ├─ QML
       └─ WindowsMediaControls
```

- Protocol 不认识“标题好不好看”，也不读取 Ui 的过滤规则。
- Ui 不解析 DLNA DIDL；它只消费中立 `MediaRequest`。
- 原始 DIDL 和当前/下一条网络媒体记录归 Protocol，Ui 掉线不影响 SOAP 查询。
- QML 和 SMTC 不准各做一套过滤或封面回退。

## 二、Protocol 保留什么

DLNA 适配器解析 DIDL 后，把未过滤字段填入中立 `MediaRequest`：

- `uri`
- `title`
- `artist`
- `creator`
- `album`
- `subtitle`
- `description`
- `longDescription`
- `artworkUri`（`upnp:albumArtURI`）
- `kind`
- `protocol`
- `metadata`（原始 DIDL）

其中原始 `metadata` 只留在 Protocol。发送给 Ui 的播放命令会清空该字段，避免
把协议专属 XML 当成 Ui 数据模型的一部分。

`DlnaSession` 另外保存原始当前/下一条记录。即使 PlaybackPipe 断开、Ui 被销毁，
`GetMediaInfo` / `GetPositionInfo` 仍从这份协议记录回答，而不是从 Ui 快照回答。

`SetAVTransportURI` 是事务式的：播放器真正报到 `Playing` / `Paused` 且加载成功后，
Protocol 才把新记录提交为 current。Open 超时或命令迟到不会覆盖旧记录；进入过
新媒体边界的加载失败会清空 current/next/previous，避免 Ui 实际停在失败媒体时
Protocol 还声称旧媒体有效。新 owner 边界会让旧命令失效，旧队列不能越界复活。
`Previous` 的可用性同样只来自 Protocol 自己记录的历史，不读取 Ui 自行攒下的队列。

## 三、Ui 统一管线

规则文件：

```text
config/metadata-pipeline.json
```

它只复制到 `MCast.Ui.exe` 旁边。文件缺失或 schema 错误时，Ui 使用内置安全规则
并在日志中说明。

JSON 只选择固定的数据来源和纯函数动作，不执行任意 JS。当前支持：

- `protocol.*`：Protocol 传来的未过滤中立字段
- `file.*`：MPV 读到的文件标签
- `uri.title`：从 URI 文件名推导
- `media_kind` / `unknown`：本地化兜底
- `file.artwork` / `protocol.artwork_uri`：封面候选

标题链：

```text
协议标题
  -> MPV 文件标签 title
  -> URI 文件名
  -> 视频 / 音频 / 图片
  -> 未知
```

艺术家、专辑：

```text
协议字段 -> MPV 文件标签 -> 空
```

副标题：

```text
音频：协议歌手 -> MPV 歌手 -> 协议专辑 -> MPV 专辑 -> 未知
视频/图片：协议副标题 -> MPV description/comment -> 未知
```

每个候选值都要先经过公共的占位符和 URI 检查，再应用对应字段的正则；只有标题
还额外应用长度、数字比例等“看起来像不像标题”的启发式。不能把标题规则套到
艺术家、专辑或副标题。

当前视频/图片副标题还会过滤已确认的播放器噪声：

```text
^vid:[A-Za-z0-9]+$
^[A-Za-z0-9_-]{200,}$
^Bilibili VXCode Swarm Transcoder(?:\s+v[\d.]+)?$
```

规则只作用于副标题，不作用于标题；音频副标题来自歌手/专辑，也不受这组规则
影响。`config/metadata-pipeline.json` 与内置回退规则保持一致。

MPV 连续输出的 `Packet corrupt` 日志会聚合成“开始 / 结束 / 总条数”，避免
每包一条把 Ui 日志刷满；其他 mpv 日志仍原样保留。

## 四、占位符

vivo 相册实际发送过拼错的 `unkown`。规则文件必须保留这个原始 token，不能
只在代码里把它纠正成 `unknown`。两者目前都列在 `placeholders` 中：

```json
["unkown", "unknown", "..."]
```

匹配会剥掉外层 `<...>`、`"..."`、`'...'`，因此 `<unkown>` 也能识别。

## 五、封面

优先级按产品决定：

```text
Protocol 的 albumArtURI
  -> MPV 内嵌封面 / MPV 识别到的外部封面
  -> 无封面
```

同一媒体只选一个最终封面。控制点已经提供 `albumArtURI` 时，MPV 随后读到的
文件封面不会再次覆盖它；只有协议没有封面时，才回退到 MPV。控制点自己可能给
视频截一帧并通过 `albumArtURI` 传来，但它仍按协议封面处理；当前实现不会在本地
给普通视频截首帧。音乐专辑封面和视频协议封面走同一条展示路线，不会出现
“协议封面先显示、文件封面再把它清掉”。

`MpvCore` 从 `track-list` 找 `albumart` 轨道：

- 外部封面有 `external-filename`：直接交给 Ui。
- 内嵌封面：等文件加载后通过 `screenshot-raw` 提取，保存成临时 PNG。
- 如果第一帧还没准备好，会在 `playback-restart` 重试，最多两次。
- 文件封面只接受本地文件；协议 `albumArtURI` 只接受 `http` / `https`，不能让
  不可信控制点借 `file://` 读取本机图片。
- 标签和封面信号都带实际媒体 URI；换条目后，上一条迟到的信号会被 Ui 丢弃。

最终 `NowPlaying.artworkSource` 同时供 QML 和 `WindowsMediaControls` 使用。
SMTC 用 `DisplayUpdater.Thumbnail(...)` 设置系统缩略图。

文件封面不走本机 HTTP 中转。`WindowsMediaControls` 读取临时 PNG 后，用
`SHCreateMemStream` + `CreateRandomAccessStreamOverStream` 构造 WinRT
内存流，再交给 `RandomAccessStreamReference::CreateFromStream`。这样做是因为
实测发现：冷启动时第一次把 `http://127.0.0.1/...` 交给 SMTC 的
`CreateFromUri`，系统可以接受对象但不会来请求图片；先设置过一次协议 HTTP
封面后，本地 URI 才会开始工作。内存流不依赖 WinRT 的 URI 惰性加载状态。
协议自带的远端 `http/https` 封面仍直接使用 `CreateFromUri`。

网络图片只有一个 URL 时，SMTC 异步读取；QML 也使用同一 URI。不会一边读网络图、
一边另外抽一张 MPV 图。

## 六、Windows 媒体面板

SMTC 已由 `MCast.Ui` 持有，宿主是 Ui 进程内一个常驻的隐藏 `Qt::Tool` 窗口。
原因：

- mpv、实际进度、音量、队列和 `NowPlaying` 都在 Ui。
- 主窗口销毁后，Ui 进程也随之结束，SMTC 不应继续显示已经暂停的旧内容。
- 面板按钮直接调用同一个 `PlaybackController` 入口，再把状态快照经
  PlaybackPipe 报给 Protocol，不直接操作 mpv。
- Ui 主流程只依赖协议无关的 `platform/MediaControls.h`，调用
  `createPlatformMediaControls()` 和 `initialize()`。隐藏宿主窗口、SMTC
  状态映射、进度/队列同步和按钮回调都封在
  `platform/windows/WindowsMediaControlsService.cpp`。

## 七、传输字段

PlaybackCodec 对以下字段都有明确编码：

```text
uri / metadata / title / artist / album / description / artworkUri /
protocol / kind / source / mediaSizeBytes
```

但边界是：

- `metadata` 的权威副本在 Protocol，Ui 命令中为空。
- `mediaSizeBytes` 的实际值由 Ui 的 mpv 查询，Protocol 只缓存回传快照。

单个 `MediaRequest` 编码后不得超过外层 IPC 字段上限（256 KiB）。HTTP 请求体
即使更大，超出上限的 URI 元数据也会在 Claim 前返回 SOAP 402。

## 八、Protocol 规划与 Ui 播放策略

LANERC 把一个普通 `.m3u8` HLS 的分片地址伪装成 PNG，而不是 MPEG-TS 或
fMP4。libmpv 0.41 和 0.42 的 HLS 解复用器都会在这里报：

```text
image2: Custom AVIOContext makes no sense
hls: Could not find codec parameters ... (Video: png, none)
error reading packet: Invalid data found
```

抓包和首段二进制检查进一步确认：LANERC 的 PNG 只是很短的壳，`IEND` 后面
直接跟着完整 MPEG-TS（首字节 `0x47`，内含 H.264/AAC），不是有效画面。
这些 10×10、11×11 的彩色壳图如果交给 `mf://`，只会得到低帧率糊块。

本次样本中，清单地址位于 `filev2.jngaoke.cn`，分片却位于
`growth-img.xhscdn.com` 这类大厂图片 CDN。现有公开资料没有发现 LANERC 自有的
投屏兼容规范或渲染器 SDK；它交给 DLNA 的仍是一条普通 `.m3u8`。因此更合理的
判断是：这是上游媒体的分发型式，用图片扩展名借用大厂 CDN，而不是 LANERC 定义
了一套新的 DLNA 播放协议。兼容层不能按域名或“LANERC”写死，必须按清单结构和
分片内容识别；这样 CDN、域名或壳格式变化时仍能回到同一条中性路线。

识别与执行分开。`MCast.Protocol` 的 `DlnaPlaybackPlanner` 负责读取清单、
解析分片和探测首段；`PlanningPlaybackGateway` 在后台完成网络预读，因此不会
阻塞 SOAP/HTTP 线程。跨越进程的不是“LANERC”这个协议特例，而是一份中性的
`MediaRequest`：

- `Native`：原 URI 直接交给 MPV。
- `ImageSequence`：带逻辑 URI 和帧表，执行 `mf://` 图片序列策略。
- `WrappedTransportStream`：带逻辑 URI 和分片表，执行本地剥壳代理策略。

```text
Protocol: 媒体 URL（.m3u8）
  -> DlnaPlaybackPlanner 读取清单
  -> 仅当所有媒体段都是图片时接管
  -> 解析 EXTINF + 相对/绝对图片 URL
  -> 探测首段是“纯图片”还是“PNG 壳 + MPEG-TS”
       ├─ 纯图片：MediaRoute::ImageSequence
       └─ PNG 壳 + TS：MediaRoute::WrappedTransportStream
  -> 通过 IPC 发送完整计划

Ui: 执行同一套 PlaybackController / 队列 / 音量 / 画面参数
  -> ImageSequence：mf:// + 虚拟时间轴
  -> WrappedTransportStream：本地代理剥壳后交给 MPV
  -> Native：原 URI 交给 MPV
```

若清单不是“全部为图片”（普通 HLS、master playlist、解析失败或网络失败），
立即按原 `.m3u8` 地址交给 MPV，不改变正常视频的播放路径。

伪装的 MPEG-TS 分片不能整份缓存后再起播：整部片有数百段。Ui 的本地代理随 MPV
的 HLS 预读按需取当前段，只对 PNG 头做一次 256 KiB Range 探测，再 Range 取
剩余 TS，因此不会在开播前下载完整影片。代理只监听 `127.0.0.1` 的随机端口。

只有“所有分片确实都是纯图片”的清单才走 `mf://`。MPV 对 `mf://` 不提供
可信的 `duration` / `time-pos`（实测均为 0），所以这种少数情况仍由
`MpvCore` 按 `EXTINF` 维护虚拟时间轴。

当前 `mf://` 以整条序列的平均 FPS 驱动画面，控制点与虚拟时间轴按逐段
`EXTINF` 计算。两者在等时长图片序列上一致；若控制点给出明显不等长的图片帧，
上屏切换时刻仍可能偏移，后续需要单独做逐帧时长调度。

类型判断仍保留两层：Protocol 的 `kind` 只是提示；文件真正打开后，
`MpvCore::mediaKindChanged` 报出的实际轨道优先。这是为了处理控制点把视频
标成 `audioItem`、却实际送来视频的情况。图片序列和包装 TS 计划则明确声明为
`Video`，即使 MPV 把单个 `mf://` 图像误报成图片，也不能把播放路线降成“图片”。

## 九、信息面板的数据来源

信息面板分两部分，边界与媒体数据一致：

- 上方：连接与协议事实，来自 Protocol；随权威 `PlaybackSnapshot.castSession`
  一起跨进程，不在 UI 重连后依赖一次性的边沿命令。
- 下方：容器、时长以及视频/音频轨，来自 Ui 本地 `MpvCore` 的 `mediaInfo`。
- 未投送时上方只显示“未投送”；有连接但未播放时下方只显示“未播放”。
- 没有视频轨时不显示视频组；字段值缺失时对应整行省略。
