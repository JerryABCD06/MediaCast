# 迁移顺序与验收门禁

基线：`6c990a3`

## 1. 工作分层

整体分为三块，顺序固定：

```text
1. 搭 Avalonia UI
2. 接 Shell 生命周期与设置
3. 接 Protocol/Playback 中性快照与命令
```

三块都必须服从同一条状态所有权契约。UI 不是第三套协议或播放器。

## 2. 阶段与提交顺序

### 阶段 0：干净基线与契约

交付：

- 本目录四份契约文档;
- 基线 CTest 和构建证据;
- 事故分支隔离说明。

退出条件：

- `main` 不包含事故实现;
- 未跟踪用户文件没有被删除;
- 冻结目录的 diff 为空。

### 阶段 1：Qt-free native host 骨架

只建立：

- UI 进程内 native host;
- Qt-free event loop;
- UiSession 生命周期;
- 不启动窗口、不创建 MPV 的 confirmation-only 路径;
- C ABI 或等价稳定接口。

此阶段不迁移页面，不改变 Protocol/Shell/wire。

### 阶段 2：MPV + Avalonia 渲染最小链

只建立：

- 一个最小 Avalonia 窗口;
- 一个 persistent OpenGL surface;
- MpvCore + render context;
- renderer projection、首帧和 PlaybackUiReady。

必须完成 `03-MPV与Avalonia渲染契约.md` 的阶段 0B 验证。

### 阶段 3：只读 UI

实现：

- Fluent 主窗口骨架;
- 顶栏;
- 投送状态;
- 当前媒体摘要;
- 媒体栏静态状态;
- 设置页标准 Fluent 导航;
- Shell 快照和语言目录消费。

禁止写回播放状态。所有显示字段都要能追溯到唯一 projection。

### 阶段 4：生命周期与关闭

按单一问题提交：

1. window shown/first frame;
2. graceful close;
3. Playback 暂停与状态 flush;
4. render detach;
5. ControlPipe 断开 fail-closed;
6. EndSession;
7. window close timeout。

每个提交必须证明退出顺序，不留下 writer/read thread 和 render callback。

### 阶段 5：ControlPipe 与 PlaybackPipe 故障路径

先做 ControlPipe 断管失败关闭，再做 PlaybackPipe 单飞重连。

PlaybackPipe 重连验证：

```text
Ui PID 不变
MainWindow 不变
MpvCore 不变
renderContextGeneration 不变
旧 PlaybackBridge 已停止
最多一个重连任务
PlaybackReconnected 已发送
PlaybackUiReady 再次发送
```

若 Protocol 需要修旧 listener 释放顺序，暂停 UI 工作，按核心提案单独确认。

### 阶段 6：播放事实与媒体边界

依次接入：

1. state / load status;
2. playerAvailable / rendererReady;
3. peerConnected / CastSession;
4. current / next / hasNext / hasPrevious;
5. position / duration;
6. media epoch 与迟到事件过滤;
7. 自然结束和换片摘要顺序。

媒体边界回归必须覆盖：

```text
Open A -> Open B
A 的迟到 metadata/artwork
B 加载失败
B 被取消
断线后重连
旧 generation 命令
```

旧媒体事件不能覆盖新媒体，UI 不能自行推进队列。

### 阶段 7：文本、设置和封面

顺序：

1. UTF-8/JSON/URI 文本边界;
2. Shell projection / patch 版本;
3. 画面值恢复;
4. 拖动时实时播放器值，松手持久化;
5. 封面 URI 和本地文件校验;
6. 元数据过滤单管线。

必须测试非 ASCII 标题、JSON 转义、URI 等价性、无效封面和不带标题媒体。
UI 不能按 UTF-16 code unit 破坏协议文本。

### 阶段 8：OpenGL context lost

实现 fail-closed：

- 暴露 context lost;
- 停止 renderer ready;
- 停止普通媒体命令;
- 受控退出或重新 attach;
- 记录 generation 和失败原因。

主动重建 render context 并不能保持播放位置时，不得声称“无缝恢复”。

### 阶段 9：confirmation-only

独立路径：

- 不创建主窗口;
- 不创建 MpvCore;
- 不创建 PlaybackBridge;
- 只使用 ControlPipe 确认请求/决定;
- 关闭确认窗口即退出;
- Shell 冷启动需要专用窗口 ready 信号，不能用主窗口 UiFirstFrame。

### 阶段 10：Wrapped-TS

保持 Protocol 规划、Ui 执行的中性边界：

- Protocol 识别图片列表和 PNG 壳 TS;
- UI 只执行 Native / ImageSequence / WrappedTransportStream;
- Wrapped-TS 代理按需 Range 读取，不整片缓存;
- 固定 worker 和 stop token;
- 超时、字节 LRU、socket 关闭所有权可证明;
- 真实 HTTP 样本 E2E。

若要求 UI 自行识别协议/CDN 特例，立即停止并重新审议边界。

### 阶段 11：真实交互、可访问性和窗口

按独立提交完成：

1. 播放/暂停;
2. Seek;
3. 上一首/下一首;
4. 音量/静音;
5. 画面调节;
6. 媒体菜单;
7. 信息浮层;
8. 设置导航;
9. 全屏;
10. UIA 和焦点;
11. 窗口移动/resize;
12. SMTC。

每项必须有真实操作步骤和日志证据，不能只靠 ViewModel 单测。

### 阶段 12：生产替换和交付

- 保留旧 UI 直到用户验收;
- 通过显式构建开关选择新 UI;
- Debug/Release CTest 全通过;
- 三进程 Qt 依赖检查通过;
- Release 目录完整;
- 生产路径不存在 Fake/Fallback 状态机;
- 文档记录已知缺口;
- 清理时只删除明确生成的构建产物，不删用户文件。

## 3. 每项提交固定流程

```text
1. 写清行为矩阵的一行
2. 标明唯一状态所有者
3. 标明唯一输入入口
4. 只改这一条链路
5. build
6. 跑相关测试
7. 真实操作或提供操作验收包
8. 读日志证明顺序
9. 显式 git add 对应文件
10. 提交
```

禁止 `git add .`。一个提交只解决一个独立行为。

## 4. 核心层闸门

以下任一变化都属于核心修改：

```text
Protocol
Shell
wire/PlaybackCodec
owner/claim/epoch
Playback command semantics
settings protocol
process lifecycle protocol
```

必须暂停 UI 工作，先写提案：

```text
原契约是什么
为什么 UI 无法消费
改动后谁仍是唯一所有者
哪些旧行为必须保持
新增哪些失败路径
需要哪些回归测试
```

用户确认后才能实施。

## 5. 验收证据

每项功能归档：

```text
commit
用户操作步骤
前置状态
预期可见结果
日志关键点
失败复现方式
构建/测试命令
```

以下说法无效：

```text
“界面看起来正常”
“单元测试通过”
“截图能显示”
“应该没问题”
```

## 6. 当前核心待确认项

从历史事故中确认过、但尚未重新在干净 `main` 上批准或实现的事项：

1. PlaybackPipe 重连前旧 server 实例的释放顺序;
2. Shell 在 confirmation-only 场景自动冷启动的 ready 契约。

在用户确认前，这两项只能保持为提案，不能顺手修改核心层。
