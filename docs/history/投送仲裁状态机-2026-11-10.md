# 投送仲裁状态机（2026-11-10 历史快照）

> **历史文档：** 本页“真实 DLNA Claim 尚未接入”和“抢占默认关闭”已经过时。
> 现行状态机、生产策略和 DLNA 权限矩阵见 `docs/投送仲裁与确认.md`。

最后更新：2026-11-10

这份文档固定多协议投送的唯一所有权语义。实现入口是
`src/cast/CastArbiter.{h,cpp}`；它不依赖 Qt、DLNA XML 或任何具体协议。

## 1. 三个独立策略

以下三件事必须分开：

| 策略 | 含义 |
|---|---|
| 是否可发现 | 新控制点能否在搜索列表里看到本机 |
| 是否可建立投送 | 新请求被接受、拒绝，还是进入用户确认 |
| 是否可抢占 | 已有投送时，新请求能否申请取代当前所有者 |

“关闭抢占”不等于“从网络里消失”。投送中隐藏设备是独立的发现策略，本轮没有
接入仲裁器。

默认策略：

- 抢占关闭；
- 抢占前需要确认；
- 确认超时 10 秒；
- 旧协议退场超时 5 秒；
- 同一时间最多保留 8 条正在退场的旧会话记录。

## 2. 唯一所有者和完整状态

任何时刻只有一份 `ArbitrationSnapshot`：

```text
revision                 状态版本；任何可见快照变化都递增
phase                    Idle / Preparing / Active /
                         ActiveWithPendingClaim / IdleWithPendingClaim /
                         Handoff / Faulted
owner                    当前所有者；不存在第二个 owner
pendingClaim             唯一待确认候选
retiringSessions         正在向旧协议告别的历史会话
lastEpoch                所有权代次
lastFailure              最近一次失败原因
```

关键不变量：

1. `owner` 最多只有一个。
2. `pendingClaim` 最多只有一个。
3. 只有所有权真正改变时才递增 `lastEpoch`。
4. `revision` 可以在候选出现、候选消失、退场完成等快照变化时递增。
5. `retiringSessions` 中的会话不是所有者，不能继续驱动播放器或 UI。
6. 旧会话迟到的命令、事件和状态按 `session.id` 丢弃。

## 3. Claim

`ClaimRequest` 由具体协议适配器翻译成中性请求：

```text
claimId       协议请求的幂等 ID；与 protocol 共同组成全局键
protocol      DLNA / Google Cast / AirPlay / Miracast / LeLink / Vendor
peer          协议能提供的设备名称、ID 和地址
mediaTitle    给确认框和状态显示的标题
```

`(protocol, claimId)` 才是完整幂等键。不同协议可以各自从 1 开始编号，不会互相
复用决定。当前 owner 和 pending claim 还会直接从快照参与重复识别，不依赖有界的
历史决定缓存。

已经结束的历史决定只保留最近 32 项。因此当前 owner、pending claim，以及最近确认
结果的重复请求可以稳定幂等；更早的拒绝/超时结果在大量新 Claim 后允许返回
`NotFound`。协议适配器不应依赖无限期重放旧 Claim ID。

发现设备、订阅 GENA、保持心跳、查询状态都不是 Claim。必须由协议明确表达
“要开始投送”才能进入仲裁。

## 4. 正常转换

### 空闲首次投送

```text
Idle
  -> Claim Accepted
  -> Preparing(owner)
  -> sessionReady(owner.id)
  -> Active(owner)
```

首次投送默认不弹确认框。

### 禁止抢占

```text
Active(owner)
  -> 新 Claim
  -> Busy(ActiveClaimProtected)
```

快照、owner 和 epoch 不变。

### 立即抢占

```text
Active(old)
  -> Claim Accepted(Preempted)
  -> Handoff(new, retiring=[old])
  -> sessionReady(new.id)
  -> Active(new, retiring=[old])
```

新协议立即开始准备；旧协议退场并行执行，不阻塞新所有者。旧协议报告退场完成
后从 `retiringSessions` 移除；超时也会清理，但不会回滚新所有者。

### 抢占前确认

```text
Active(old)
  -> Claim AwaitingConfirmation
  -> ActiveWithPendingClaim(old, candidate)
```

这时：

- 旧投送仍是 owner，继续播放和接收命令；
- epoch 不变；
- 不能向旧协议发送结束通知；
- 其他 Claim 返回 Busy。

用户确认后：

```text
ActiveWithPendingClaim(old, candidate)
  -> Accepted
  -> Handoff(candidate, retiring=[old])
```

用户拒绝或 10 秒超时：

```text
ActiveWithPendingClaim(old, candidate)
  -> Active(old)
```

只清除候选；旧会话没有任何所有权变化。

确认调用自己也会检查 deadline。即使调度器还没来得及调用 `tick()`，只要确认到达
时已经到点，也一律按 `ConfirmationTimedOut` 处理，不能被接受。

### 确认的进程间消息

ControlPipe 上新增确认消息，IPC minor 逐步升到 `2`：

```text
Protocol -> Shell  CastConfirmationRequest
Shell -> Protocol  CastConfirmationDecision
```

请求携带：

```text
protocol
claimId
peerId / peerDisplayName / peerAddress
mediaTitle
remainingTimeoutMs
```

决定用响应 flag，`correlationId` 指向请求的 `messageId`，并带回同一个
`(protocol, claimId)` 与 `accepted`。Shell 不解析 DLNA/Cast/AirPlay 报文，只负责
显示中性的确认请求。

候选还没有 session 所有权，因此这两条消息的 `sessionId` 和 `stateVersion`
当前都固定为 `0`，不能拿来代表仲裁 revision；幂等与关联只使用
`(protocol, claimId)` 和 `correlationId`。`peerId` 必须是非空有效 UTF-8，
其余展示文本允许为空但必须是有界有效 UTF-8。

Shell 收到请求后，按 Protocol 连接代次和绝对 deadline，把它转换成
`UiCastConfirmationRequest` 发给 `MCast.Ui.exe`。UI 用独立 Fluent 窗口显示，
主窗口不参与，也不会被主动置前。确认窗口：

- 使用 QML + FluentUI，只显示关闭按钮，隐藏最小化和最大化；
- 默认按钮是“继续当前投送”；
- 点击右上角关闭与“继续当前投送”相同，都是拒绝接管；
- 显示带倒计时的进度条并只把自己置前；
- 超时、关闭、对话框失败和 Protocol 连接失效都 fail-closed；
- Shell 切换 UI/Protocol 连接时发送 `UiCastConfirmationCancel` 关闭旧窗口；
- 入队时保存绝对 deadline，UI 启动或排队较慢时不会延长仲裁等待；
- 按 `messageId + protocol + claimId` 缓存最近结果，避免重复弹窗或错误复用。

UI 的 QML 引擎可以脱离主窗口，单独创建这扇确认窗口；
`MCast.Ui.exe --confirmation-only` 提供确认专用运行模式。原生 Task Dialog
只保留为手动烟测，不属于生产路径。

v1.1 的 Protocol↔Shell 确认消息要求 `versionMinor >= 1`；v1.2 的 Shell↔UI
确认转发消息要求 `versionMinor >= 2`。帧解码同时拒绝高于本机的 minor。
当前三进程仍靠 executable hash/build ID 要求同一次构建，不支持跨 minor
子进程混跑。将来若要混版，必须先把 Hello 的对端 minor 保存下来，并
按双方共同能力决定是否启用确认流程。

### 待确认时旧投送自然结束

```text
ActiveWithPendingClaim(old, candidate)
  -> old ended
  -> IdleWithPendingClaim(candidate)
```

候选最多仍保留到原确认 deadline。用户接受后从空闲状态建立新会话，不再产生
“抢占”；拒绝后回到 Idle。

## 5. 失败和退场

- 当前 owner 正常完成、用户断开或关闭：回到 Idle。
- 当前 owner 报告 Failed / ProtocolLost 且没有待确认候选：进入 Faulted。
- 当前 owner 失败但已有待确认候选：进入 IdleWithPendingClaim，候选仍由用户决定。
- 新所有者在 Handoff 中失败：进入 Faulted 或 Idle，不能恢复已经被结束的旧会话。
- 旧协议告别失败只记录退场超时，不影响新所有者。
- 策略变更只影响之后产生的 Claim；已存在的 pending deadline 不随设置变化。
- `Preparing` / `Handoff` 的协议 watchdog 尚未放进仲裁器；协议适配器必须明确发
  `sessionReady`、`sessionEnded` 或 `sessionRetired`，不能让状态永久悬空。

## 6. 同一协议与设备身份

`owner` 表示当前协议会话，不假装能跨协议唯一识别物理设备。

- 同一协议内多个控制点连接到同一个 transport/session 时，协议适配器先用本协议
  能提供的信息形成 Claim。
- IP、设备名或 DIDL 字段只能作为显示和辅助判断，不能作为跨协议身份认证。
- 同一物理设备通过另一种协议再次投送，默认仍视为新 Claim。

## 7. 当前边界

已实现：

- Qt-free `CastArbiter` 纯状态机；
- 无抢占、立即抢占、确认抢占；
- 拒绝、超时、重复 Claim；
- 旧投送在待确认和拒绝期间保持不变；
- 旧所有者自然结束时的空闲候选；
- 退场记录、退场完成和退场超时；
- `ArbitrationSnapshot`、`ClaimDecision` 和自动测试。
- UI 独立 QML 确认窗口、倒计时、取消、置前和双向 ControlPipe 转发。
